# План реализации

Актуальный приоритет 2026-10-08: S4, повседневный UX. Tasks 1–7 [адаптации C11–C17](superpowers/plans/2026-10-07-optional-scheduling.md) завершены и прошли финальные независимые reviews и root checks; факты и ограничения — в [STATUS](STATUS.md). Правила необязательных сроков и CPM заданы [принятым нормативным приложением](superpowers/specs/2026-10-07-optional-scheduling-policy-proposal.md). S2–S3 ниже фиксируют историческую реализацию; C11–C17 имеют приоритет над прежними defaults.

S0–S3 и адаптация необязательных сроков реализованы. Первый релиз требует завершения S4–S6.

Не оценка календарных сроков и не обещание готовности. Каждый этап заканчивается запускаемым результатом и проверками. Разрабатывать последовательно сквозными сценариями, не отдельными несвязанными картинками.

## S0 — безопасный фундамент

**Вход:** комплект размещён в Git-корне; существующие файлы проверены; agent instructions прочитаны.

Установить/проверить Node и package manager; выбрать поддерживаемые совместимые версии, зафиксировать patch и lockfile. Не регенерировать проект командой scaffold поверх корня. Добавить TypeScript strict, lint, formatter, тесты domain/API/UI, skeleton клиент/сервер и проверяемые npm-команды. Сохранить kit checks отдельными от app tests.

Проверить `.gitignore`, `.dockerignore`, local hooks, Gitleaks и CI. Не добавлять API-ключей для агентов. Подготовить однообразные dev/start/build/test/typecheck/lint и описать в README. Добавить минимальные `/healthz` и `/readyz`, структуру миграций и test DB во временной директории. Dockerfile/compose без реальных настроек. Пароль/admin setup реализовать до любого внешнего доступа.

**Выход:** пустое приложение и API запускаются локально, проходят реальные smoke-tests; проект имеет воспроизводимую сборку. Документированы версии и команды. Если недоступен network/Gitleaks/browser, честно зафиксировать blocked; не имитировать успешный прогон.

## S1 — первый сквозной сценарий

SQLite + проект + task CRUD + сворачиваемое дерево произвольной глубины. Быстрый ввод, изменение порядка/родителя, защита от parent-cycle, выбор задачи и компактная правая панель по выбранному варианту. Необязательные даты сохраняются как пользовательский ввод без фиктивных полос.

**Выход:** создание/изменение/удаление/восстановление задачи; после перезапуска данные на месте. Empty/loading/error states и keyboard. Integration tests реальной SQLite; не только in-memory mocks. Layout совпадает по характеру с выбранным главным экраном.

## S2 — расчётное ядро, не UI-имитация

Чистый domain scheduling module, FS-DAG, рабочие дни, partial/unscheduled, auto/fixed, summary, critical tasks/edges, projectFloat/constraintFloat, диагностические конфликты. Все numerical fixtures и дополнительные тесты проходят. API команды с revision, operationId и атомарным undo.

**Выход:** сценарии смены критического пути, равных ветвей, unknown, fixed conflict, parent conversion, календаря и rollback проверены. Изменение задачи возвращает согласованный schedule result. Данные не зависят от того, что открыто на экране.

## S3 — Гант и выбранные зависимости

Общее дерево строк + шкала, дни/недели/месяцы, today, sync scroll, полосы, summary, критичность, dependency arrows, drag/resize. Tasks without dates не получают полос. Панель зависимостей — выбранная вертикальная схема непосредственных соседей. Добавление/удаление связи, цикл с объяснением, выбор соседней задачи, показать на Ганте.

**Выход:** изменение подзадачи действительно сдвигает допустимые зависимые работы, границы родителей и критический путь. Undo возвращает весь план. Полезный core, но V1 не объявляется завершённой до приёмки S5–S6.

## S4 — законченный повседневный UX

Вкладка подзадач переиспользует дерево; исключённый коллаж не применять. Поиск/фильтры с родительским контекстом. Иерархическая доска с передачей статуса без изменения parent. Демонстрацию ещё не утверждённого board layout показать владельцу; не добавлять дополнительные корпоративные функции.

**Выход:** согласованные представления одних задач; нет плоской доски, теряющей контекст. Переходы и клавиатурные команды проверены. Все кнопки работают или скрыты.

Последовательность небольших задач S4:

1. Поиск по названию и фильтр по статусу: совпадения вместе со всеми родителями, общий порядок дерева/Ганта, без записи или пересчёта плана. [План первой задачи](superpowers/plans/2026-10-08-s4-task-filters.md).
2. Реализована вкладка «Подзадачи» на общем дереве и быстром вводе: произвольная глубина, отдельные черновики, переходы, возврат фокуса и состояния. Рабочее уточнение D15; проверки — в [STATUS](STATUS.md).
3. Подготовлен [прототип иерархической доски](../design/prototypes/hierarchical-board.html) на синтетических данных для проверки владельцем; компоновка пока не утверждена (O03).
4. Подключение проверенной компоновки доски к серверным изменениям статуса и undo; сохранение parent, дат и связей; сквозная приёмка S4.

## S5 — данные и защищённое self-hosted развёртывание

Довести аутентификацию/сессии, local admin setup, безопасные логи, validate input, limits, CSRF/origin. Реализовать versioned export/import, consistent backup и проверенное восстановление. Production non-root image, persistent volume, loopback binding по умолчанию, healthchecks, graceful shutdown. Проверить повторный запуск и upgrade миграций на копии synthetic DB.

**Выход:** один production-контейнер. Перезапуск не теряет данные; restore подтверждён тестом. Нет реальных данных/секретов ни в Git, ни в image layers или runtime build context. Изоляция front/server данных проверена.

## S6 — релизная приёмка

Выполнить полный ACCEPTANCE, замеры на синтетическом наборе целевого размера и screenshot review двух viewport. Проверить git history, privacy guard, Gitleaks, dependency audit и публичные артефакты. README содержит только проверенные команды и честные ограничения.

**Выход:** владелец может поставить leaf по инструкции с чистого checkout. Релиз и push делаются только после разрешения владельца; наличие задачи не является разрешением публиковать всё автоматически.

## Правила разбивки задач

Один task/PR решает одну проверяемую проблему. В нём: цель, границы, файлы/контракты, критерии приёмки, проверки, known limitations. Не открывать одновременно два PR, меняющих схему или scheduling contract без согласования. Не оставлять «временно» выключенные защитные проверки.
