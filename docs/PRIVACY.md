# Публичный репозиторий: секреты и личные данные

**Главная защита — не давать dev-агентам production-данные.** Разработка ведётся на синтетических задачах и отдельной пустой БД. Игнорирование файла Git не запрещает агенту читать его и не защищает существующую историю.

## Что никогда не публикуется

Реальные задачи/проекты/описания, личные адреса и контакты, логи использования, SQLite и WAL/SHM, дампы SQL, экспорты, backups, uploads, вложения, cookies, browser storage/traces/HAR, access tokens, приватные ключи, production `.env`, session/password hashes, реальные hostnames/пути инфраструктуры, credential store и transcript/memory агента, содержимое домашнего каталога.

Явное исключение: владелец может разрешить публичный Git identity email только в соответствующих полях автора/коммиттера. Область разрешения задаётся в `config/public-git-metadata.json`; остальные персональные данные и секреты остаются под прежними запретами.

В docs/fixtures использовать только явно синтетические сведения: «Демо-проект», задачи A/B/C, example.test и loopback. Выбранные макеты уже обезличены; остальные скриншоты из беседы сюда не переносить. Никогда не превращать реальный экспорт в test fixture, просто изменив имя файла.

## Четыре слоя защиты

**1. Изоляция.** Production storage и secrets за пределами checkout/build context; не монтировать их в sandbox агента. Раздельные dev/prod аккаунты. Agent auth хранится средствами Codex/Claude вне проекта; leaf не нуждается в их ключах.

**2. Git и Docker.** `.gitignore` покрывает runtime/local data, `.dockerignore` построен как allowlist build inputs. Но уже tracked файл игнорированием не удаляется (источник S09). Не использовать `git add -f` для обхода защиты. Проверять staged blobs, не только рабочие файлы: секрет мог быть staged раньше, а потом затёрт в рабочем дереве.

**3. Локальная проверка.** Privacy guard проверяет запрещённые пути, известные secret patterns, некоторые PII-маркеры и бинарные assets. Gitleaks добавляет полноценные правила известных секретов; pre-push сканирует историю, включая удалённые позднее файлы, изменения merge-коммитов, сообщения коммитов, annotated tags и их identity headers. History scan использует `--all --full-history --diff-merges=separate`, чтобы не пропускать секреты, добавленные только результатом слияния. Commit-msg проверяет ещё не созданное сообщение коммита. При отказе/отсутствии scanner push не проходит через установленный hook. Это не защита от намеренного обхода Git hooks.

**4. Сервер и review.** Включить доступную GitHub push protection, branch rules, secret scanning; CI read-only. Перед первой публикацией человек проверяет staged diff, файлы, images, историю и metadata коммитов. Эти настройки не включаются автоматически распаковкой архива (S10–S12).

## Бинарные файлы и изображения

Новый бинарный файл, изображение, документ или архив запрещён guard до явного ручного privacy-review и записи точного пути + SHA-256 в `config/public-assets.json`. Исключение должно быть на конкретные байты, не на каталог `screenshots/**`. При изменении байтов требуется новая проверка. В manifest v2 `assets` содержит только текущие одобренные версии, а `historicalAssets` — прежние пары path/hash. При изменении сначала перенести старую пару в `historicalAssets`, затем добавить проверенную новую в `assets`. Старые пары сохранять, пока эти версии присутствуют в достижимой истории: history scan проверяет и прежние байты. Нельзя одобрять исторический файл задним числом без просмотра. Guard проверяет расширения, сигнатуры PDF/ZIP и бинарную кодировку. ASCII-PDF тоже требует approval. SQLite под чужим расширением не становится безопасным: бинарные байты также требуют review. Классификация не распознаёт все возможные форматы и способы скрытия данных.

Проверка хеша не распознаёт персональные данные. На изображении может быть токен, который текстовый scanner не видит. Не загружать production screenshots для review агента. Перед разрешением удалить метаданные и проверить всё изображение визуально. Не публиковать screen recordings, traces и CI artifacts по умолчанию.

## Ограничения guard

Встроенный guard не универсальный DLP: не распознаёт все имена, телефоны, скрытые данные в кодировках, все провайдерские токены и все изображения. Он намеренно сообщает только путь/правило или Git object ID, не значение находки. Запрещённые workspace-файлы отклоняются до чтения; приватные каталоги не обходятся. Manifest и assets читаются без следования symlink. Gitleaks запускается с полным redaction; обёртка выводит только собственные краткие итоги и не пересылает raw stdout/stderr scanner. Inline `gitleaks:allow` не подавляет проверку; `.gitleaksignore` требует отдельного изменения политики и сейчас блокируется. Не сохранять подробные отчёты в tracked tree.

Preflight проверяет рабочие файлы и staged blobs отдельными Gitleaks scans: чистая рабочая копия не отменяет находку в index. Для staged/history/commit message scanner получает снимок конфигурации из index, для workspace — из working tree. Временный снимок имеет ограниченные права и удаляется при любом обработанном результате. Незастейдженная `.gitleaks.toml` не ослабляет правила публикации; изменение staged policy по-прежнему требует review. Обёртка возвращает exit 1 для покрываемой находки и exit 2 для ошибки исполнения/конфигурации, блокируя операцию в обоих случаях.

Git hooks локальны и устанавливаются отдельно на каждом клоне; их можно обойти, поэтому нельзя давать агенту неограниченные credentials для push. Инструкции в AGENTS/CLAUDE и deny-rules не равны OS sandbox. В .claude/settings.json включены sandbox, отказ при недоступном sandbox и запрет unsandboxed retry; private Read rules дополняются filesystem/network settings. Конфигурация не доказывает фактическую изоляцию и может зависеть от версии/managed settings. Проверять runtime на синтетических данных по AGENT_WORKFLOW (S03).

## Эксплуатация leaf

Пароли не в командной строке, Dockerfile, Compose, .env.example или README. Admin setup должен читать пароль интерактивно без echo либо из локального secret-file вне репозитория; не писать его в logs. Использовать проверенное хеширование, безопасные session cookies, rate limits и CSRF/origin checks. См. ARCHITECTURE; параметры защиты проверять по S13.

База и backups содержат личные данные. Ограничить filesystem permissions; выбрать encrypted backup storage на стороне владельца. Restore и миграции сначала пробовать на синтетической или разрешённой изолированной копии. Экспорт полон по проекту, но не включает auth/session.

Не логировать titles, descriptions, тела auth-запросов, полный querystring, cookie, Authorization, переменные окружения. Для ошибок — ID запроса, код, безопасная причина. Production source maps, если нужны, хранить приватно; не вкладывать в них env/config.

## Git metadata и публичная совместная работа

Даже без private files публикация раскрывает commit authors, emails, messages, filenames и discussion text. Владелец проверяет историю и выбирает Git identity самостоятельно. Автоматический metadata scan блокирует покрываемые секреты и email за пределами synthetic/example и GitHub noreply domains (`EMAIL_REVIEW_REQUIRED`); имена и остальные сведения требуют ручного review. Реальные identity значения и их хеши не копируются в конфигурацию проекта. При intentionally public email нужен согласованный узкий вариант политики, а не общий bypass; до такого решения проверка остаётся blocking. Не придумывать его имя/email и не менять глобальный Git config. Не запускать команды, печатающие credential-bearing remote URLs.

Разрешение владельца фиксируется в [public-git-metadata.json](../config/public-git-metadata.json): точный object ID проверенного исходного коммита, поля `author`/`committer` и безопасное описание review. Guard получает одобренный адрес из этих immutable source fields только в памяти и разрешает тот же email в соответствующих полях остальных и будущих коммитов. В конфигурации нет отдельной копии адреса или его хеша. Источник должен оставаться достижимым commit object; неизвестные fields, wildcards, duplicate sources и ошибочные manifests отклоняются.

History guard использует review manifest из index, поэтому unstaged правка не расширяет разрешение. Для изменения сначала проверить public workspace и staged policy. Email в имени автора, других headers, сообщениях, файлах и annotated tags продолжает требовать review, даже если сам адрес совпадает с одобренным. Все прочие guard rules и Gitleaks проверяют исходные bytes без исключений. Одобрение identity не разрешает отправку репозитория: push/publication по-прежнему требует отдельного поручения.

Не прикладывать реальный экспорт к issue. В PR запрещены screenshot с именами реальных проектов, raw logs, transcripts и файлы scanner reports. Workflow для fork не получает secrets и deploy credentials. Изменения workflow, hooks, allowlist и scanner config рассматриваются как чувствительные.

## Если секрет уже попал в Git или был отправлен

Остановить дальнейшую публикацию. Сообщить владельцу путь/тип без значения. В первую очередь отозвать/сменить credential; удаление строки не обезвреживает действующий токен. Если это личные данные — оценить область раскрытия и удалить доступные копии с участием владельца.

History rewrite, purge artifacts, удаление releases и force-push — только после согласования. `.gitignore` и новый коммит с удалением не очищают историю и чужие clones/caches. Не обещать гарантированного удаления опубликованного материала. После исправления повторить index/history scans и проверить CI artifacts, image layers, PR attachments и tags.

## Чеклист первого push

Все изменения ожидаемы; только synthetic fixtures; нет настоящей БД/экспортов; локальные env/agent files ignored; новые binaries вручную одобрены; index и history прошли guard/Gitleaks; author metadata проверены; push protection доступна и настроена; owner явно разрешил отправку. Если хотя бы один пункт не подтверждён, не объявлять публикацию безопасной.
