# Расписание и критический путь — контракт первой версии

## Уточнение требований — 2026-10-07

Решения [C11–C17](DECISIONS.md) имеют приоритет над прежними defaults ниже:

- У задачи есть необязательные начало, окончание и длительность. Общий сценарий автоматического назначения сроков от начала проекта исключён; ввод длительности сам по себе не включает прежний Auto.
- Отдельный дедлайн исключён по C15. Необязательная дата окончания сохраняется; отдельное контрольное требование deadline и предупреждения о его превышении не входят в целевой контракт.
- Сводные сроки родителя вычисляются как минимальное начало и максимальное окончание подчинённых задач. Если полный интервал определить нельзя, сводные даты и summary-полоса не показываются. Частичный диапазон по известной части не заменяет полный сводный интервал.
- C19 расширяет C14: любая конечная задача с неполным интервалом получает приглушённую полосу. Собственное начало задаёт левый край, собственное окончание — правый; при отсутствии обеих дат используется минимум известных начал родительской группы, затем сегодня. Длина — длительность или один display-день.
- D13 уточнён C19: собственные даты приоритетнее групповой опоры, отсутствие опоры использует сегодня в timezone проекта. При обеих заданных датах отображается их интервал. Визуальные значения и fallback одного дня не сохраняются в исходных полях, не делают неизвестный интервал известным и не входят в сводные сроки или CPM.
- Иерархия и зависимости остаются разными структурами. Сводный интервал не является критическим путём.

Ниже сохранён исторический контракт, по которому реализованы S2–S3. Разделы об Auto, project.startDate, автоматическом назначении сроков по длительности, автосдвигах, deadline, partial summaries и полном запрете полос для задач без дат описывают прежнюю реализацию. Tasks 5–7 адаптировали source/storage/API/UI к C11–C17 и подключили серверный CPM по C16; исторический контракт ниже не задаёт новые требования текущей реализации. Актуальные проверки и ограничения — в [STATUS](STATUS.md).

## Явное редактирование полей — C18, 2026-10-08

В панели действует [связанный ввод, §3.3](superpowers/specs/2026-10-07-optional-scheduling-design.md): начало сохраняет длительность и пересчитывает окончание; окончание сохраняет начало и пересчитывает длительность; длительность сохраняет начало, а без него использует окончание. Расчёт после завершения ввода; очистка меняет только одно поле, одна длительность не назначает дат. Это видимый черновик атомарной команды, не фоновый Auto. Independent API patch, анализ сохранённых nullable полей, C16, summary и условное отображение сохраняют прежнюю семантику.

## Условное отображение — C19, 2026-10-08

[Спецификация C19](superpowers/specs/2026-10-08-conditional-gantt-design.md) задаёт таблицу отображения, обратный отсчёт от окончания, границы календаря и разделение server display/client today. Чистый domain helper не читает часы: today передаётся только представлением. Форма создания сохраняет явную длительность 1 (можно очистить), даты пусты; «Сегодня» задаёт начало явно через C18. API defaults и CPM не меняются.

## Принятые политики C16/C17

- Только валидная введённая pair допускает leaf task в CPM. H=max(f) общий для всех независимых компонент/done; обратный проход даёт projectFloat, а constraintFloat отдельно показывает резерв текущего размещения. Нулевое разрешение редактирования не означает project-critical; critical FS имеет два нулевых projectFloat и соседние рабочие границы. Формулы/P01–P11/N06 — в нормативном приложении и [ADR 008](adr/008-explicit-date-cpm.md).
- При incomplete общий CPM неизвестен: floats отсутствуют и global critical IDs пусты с пояснением. Датированная часть анализируется отдельными множествами по одному Hknown, только в полностью известных слабосвязных компонентах. Infeasible имеет приоритет и не выдаёт normal/partial critical results. Display/summary не являются CPM input.
- C17 однократно материализует доступные абсолютные legacy Auto/done intervals в source pair с exact private archive; done использует completed pair. Без исторической опоры даты не придумываются. Preview/digest acknowledgement перед existing legacy upgrade, temporal replay/undo и M01–M10 заданы [ADR 007](adr/007-legacy-scheduling-migration.md). Actual production operation требует отдельного поручения.

## Размещение при установке связи — C25 / рабочий D18, 2026-10-08

[Спецификация C25](superpowers/specs/2026-10-08-fs-link-placement-design.md) уточняет C24: task.edit со сроками и новым входящим ребром нормализуется тем же push, что relation-only add. Без добавленного ребра прямой source-конфликт по-прежнему отклоняется. Бездатные конечные работы размещаются после доступных real/conditional окончаний предшественников; максимум с базовой C19-опорой и полный DAG дают только геометрию. Исходные поля, authoritative FS/CPM/coverage/summary не меняются. L01–L09 задают приёмку.

## FS-каскад команд — C24 / рабочий D17, 2026-10-08

[Спецификация C24](superpowers/specs/2026-10-08-fs-dependencies-design.md) и [ADR 011](adr/011-fs-command-cascade.md) расширяют запись перед существующим чистым анализом C16. Create/edit принимают command-only `predecessorIds`; create сохраняет задачу и входящие рёбра атомарно, edit заменяет входящие endpoints при наличии поля, `[]` удаляет их. DTO/SQL задачи не получают это поле; existing dependency.create/delete используют тот же validator.

Причинный каскад активируется добавленным ребром или изменённой достоверной finish-границей source работы; fan-in использует максимум, diamond обрабатывается один раз. Неизменный max, поглощённая промежутком задержка и неизменный finish останавливают ветвь. Поздний bound переносит известный start при необходимости; ранний pull требует прежней tight-границы, неизменных endpoints и достоверных old/new finishes всех predecessors. Полная pair сохраняет рабочую длину и точную nullable duration; start-only меняет только начало. Finish-only/duration-only/null dates, conditional display, parent group и today не выводят отсутствующие даты. Отдельных anchors и режимов нет; удаление связи не меняет сроки.

Прямой конфликт source edit без нового входящего ребра (исключение C25), необходимый push done, cycle/invalid endpoints, overflow и непереносимый затронутый invalid/unavailable source дают полный rollback. Unavailable marker не снимается каскадом. GET, analysis, title/status-only, undo, cached exact retry и frozen replay не чинят historical conflicts. C16 по-прежнему диагностирует infeasible synthetic/historical snapshots; старое разрешение сохранить конфликт как infeasible не действует для нового прямого FS-конфликта активной команды C24.

Одна транзакция включает patch, cascade, summary/CPM, revision, outcome и undo. Parent criticality использует общий проектный CPM без отдельного vertex: §6.1 задаёт переключение P/Q и literal floats. Undo возвращает точные nullable source поля и IDs одним действием; exact retry возвращает сохранённый outcome без повторного переноса.

## Прежний контракт S2–S3

Это предлагаемая формализация обсуждённых требований. Она обязательна для согласованной реализации в рамках defaults D04–D12; не утверждать, что каждый математический нюанс отдельно согласован владельцем. Изменения семантики оформлять ADR и тестами.

## 1. Две разные структуры

`parentId` задаёт дерево вложенности. `predecessorId -> successorId` задаёт ориентированный граф работ. Порядок строк не создаёт зависимость. Перенос в другую ветку не меняет связи, пока все задачи остаются в проекте и конечными.

Только конечные задачи участвуют в расчёте длительности. Родитель с детьми — сводная задача. Полный пересчёт всех запланированных конечных задач проекта проще и предпочтительнее инкрементального на первом этапе.

Граф должен быть ацикличным. Отклонять цикл до сохранения, показывая понятную цепочку. Self-link и повторяющаяся связь запрещены. В V1 только FS, лаг 0, один проект, нет ресурсных ограничений.

## 2. Даты, длительности и календарь

Хранить пользовательские даты как календарные строки `YYYY-MM-DD`, не UTC-midnight timestamps. Времена создания/изменения можно хранить UTC. Часовой пояс проекта нужен для отметки «Сегодня» и берётся из настройки/локального выбора, не из скрытого предположения о владельце.

Пользовательское окончание **включительно**. Внутри расчёта — целочисленные границы рабочих дней `[start, finishExclusive)`. Длительность `d = finishExclusive - start`, минимум 1 для работы. Один день: start=0, finishExclusive=1. Отображаемая дата окончания — дата рабочего дня `finishExclusive - 1`. FS означает `successor.start >= predecessor.finishExclusive`.

Календарь един для проекта: все дни или пн–пт. Функции `dateToIndex`, `indexToDate`, `nextWorkingDay`, `workingDaysInclusive` тестируются отдельно. Нельзя добавлять дни как `24*60*60*1000` и полагаться на часовой пояс браузера. Автодаты нормализуются к следующему рабочему дню; ввод закреплённой границы на выходной не молча исправлять: предложить нормализацию с подтверждением или отклонить.

Если нет project.startDate, можно сохранить длительности/связи, посчитать относительные дни и CPM, но календарные полосы не выдумывать; показать «Укажите начало проекта». При наличии абсолютных ограничений и отсутствии даты начала календарный расчёт помечать incomplete до выбора начала.

## 3. Состояния задачи и ввод

| Состояние | Семантика |
|---|---|
| Unscheduled | Нет полного интервала/длительности; можно хранить одну дату как пометку. Никаких dummy bars. |
| Auto | Длительность известна; даты рассчитываются от начала проекта, предшественников и `notBefore`. |
| Fixed | Полный интервал закреплён. Начало и окончание не сдвигаются автоматически; длительность определяется календарём. |
| Summary | Есть дети; собственный режим работы отсутствует, даты и состояние сводные. |

Название — единственное обязательное поле при создании. Не использовать длительность 1 по умолчанию для задач без расписания. Неизвестно ≠ 0. Вехи длительностью 0 за пределами первого релиза.

Для нового несоставного элемента пользователь может:

- задать только начало/окончание: оставить пометкой, без участия в CPM;
- задать длительность: включить Auto (с явным состоянием интерфейса);
- задать обе даты: предложить и явно показать Fixed; длительность вычислить;
- задать начало и длительность: Auto + notBefore; не притворяться, что дата начала жёстко закреплена;
- задать окончание и длительность: предложить полное закреплённое расписание, явно подтверждаемое пользователем.

В Auto поля рассчитанных начала/окончания не должны создавать конкурирующие источники истины. Перенос полосы задаёт notBefore; левее разрешённого FS положения она возвращается к допустимой дате с объяснением. Правый resize меняет длительность. Изменение рассчитанного окончания через поле пересчитывает длительность относительно текущего начала. Нельзя тайно записать произвольные три противоречивых числа.

При переходе Auto → Fixed сохранить текущий вычисленный интервал. Fixed → Auto сохранить длительность и очистить фиксацию после явного действия. Удаление планирования — отдельная команда; проверить зависимые работы.

## 4. Дедлайн — прежний контракт, отменён C15

В прежней реализации `deadline` — отдельное пользовательское требование, не `computedFinish`. Он не двигается вслед за автопланом и не якорит обратный проход CPM; превышение показывается отдельно. По C15 это поле и предупреждение исключены из целевого поведения. Дата окончания остаётся самостоятельным необязательным полем; правила совместимости сохранённых данных нужно проработать при адаптации API/хранения.

## 5. Базовый CPM (без фиксаций)

Топологическая сортировка, затем прямой проход:

```text
ES[t] = max(0, release[t], max(EF[p] for p in predecessors[t]))
EF[t] = ES[t] + duration[t]
T = max(EF[t] for all scheduled tasks)
```

`release` — индекс notBefore, default 0. Обратный проход от виртуального общего окончания проекта:

```text
LF[t] = min(LS[s] for s in successors[t]), or T for a terminal task
LS[t] = LF[t] - duration[t]
projectFloat[t] = LS[t] - ES[t]
```

Все терминальные работы ведут к одному виртуальному финишу; несколько независимых компонентов не получают каждый собственный нулевой резерв. Пустой граф: T отсутствует, критических задач нет.

Критические работы имеют нулевой projectFloat. Критическая связь дополнительно должна быть tight: `EF[p] == ES[s]`. Нельзя красить связь между двумя нулевыми работами, если между ними есть ожидание, заданное ограничением. При равенстве длин ветвей показать все критические цепочки, не перечислять экспоненциальное число путей: вернуть множества task IDs и edge IDs.

Это контракт leaf на основе обычного прямого/обратного прохода CPM; базовый алгоритм и модель DAG описаны в официальном учебном [источнике S08](SOURCES.md). Примерные числа проверяются независимо от макетов.

## 6. Закреплённые и завершённые работы

Прямой проход Fixed использует ровно его границы. Если входящая работа заканчивается позже fixedStart, фиксацию не двигать: вернуть `FIXED_PRECEDENCE_CONFLICT`. Бессмысленный интервал/календарь/начало до начала проекта — отдельная ошибка. Не публиковать такой план как feasible.

**Не смешивать резерв до финиша проекта и допустимую задержку до закреплённой даты.** Для корректного fixed-плана обратный `projectFloat` считать как CPM от общего T, не приравнивая LS каждого Fixed к ES. Иначе каждая закреплённая задача ложно станет критической.

Отдельный `constraintFloat`: для анализа соблюдения существующих фиксаций в обратном проходе у Fixed задать constrainedLS=fixedStart, у обычных работ — минимум constrainedLS последователей минус длительность (терминал ограничен T). Для Fixed самого по себе «можно сдвинуть» не вычислять как разрешение: его нельзя сдвигать автоматически. UI различает «критична для окончания проекта» и «нет резерва до закреплённой работы».

Пример: A длится 2 дня; B фиксирована [5,6), ждёт A; C независима, [0,10). У A `projectFloat=7`, у B `projectFloat=4`, у C 0. Но A может задержаться лишь на 3 дня, прежде чем нарушит фиксацию B: `constraintFloat=3`. Это не одна и та же цифра.

При невыполнимых ограничениях вернуть diagnostics и proposal preview, но не показывать нормальный критический путь для всего проекта. В историческом S2–S3 сохранение пользовательского противоречивого ограничения было допустимо с явным статусом infeasible; активные команды C24 проверяются по правилам выше; прежний валидный расчёт не выдавать за новый. Вся операция атомарна.

Для `done` сохранить плановый интервал; автосдвиг завершённой работы запрещён и обрабатывается как ограничение. Отметка done не уменьшает длительность до нуля. Нет переноса от «сегодня», actual start/finish и remaining duration в V1. Возврат из done восстанавливает прежний режим после явного действия.

## 7. Неизвестная длительность и неполный граф

У незапланированной задачи без связей нет вклада в известное расписание. Охват сохраняется в результате расчёта: knownLeafCount из totalLeafCount, сводные строки не входят в знаменатель. По [C20](superpowers/specs/2026-10-08-compact-workspace-design.md) постоянная фраза «Запланировано N из M конечных задач» и предупреждения о недостающих датах на главном экране не показываются. Это изменение presentation, не расчёта.

Если незапланированная работа участвует в связях, пометить её и зависимых от неё потомков графа как blocked-by-unknown. Не считать неизвестную длительность нулевой. Известные независимые компоненты можно показать, но общий прогноз и CPM пометить `incomplete`. Подсветка относится только к известной части, подпись «Предварительный расчёт» обязательна.

Для unknown-последователя известной задачи тоже нельзя объявлять завершение проекта полным: исходящий неизвестный остаток остаётся в охвате. Весь цепочечный контекст нужен для диагностики.

Сводные даты вычисляются по известным конечным потомкам, а summary получает признак partial, если часть потомков не запланирована или blocked. Это не маскируется под окончательное окончание этапа.

## 8. Дерево и преобразования

У summary начало=min(starts), окончание=max(finishes). Длительность summary — охват по календарю, не сумма длительностей параллельных детей. Незапланированные дети не получают дат из родителя.

При добавлении первого ребёнка к запланированной или связанной работе предложить «Сохранить собственную работу отдельной подзадачей». В одной транзакции создать work-child, перенести собственные сроки/режим/статус/связи на него, сделать бывшего родителя summary. Не переносить сроки на случайного нового ребёнка и не терять внешние зависимости. Для пустой незапланированной задачи превращение в summary безопасно без дополнительной работы.

При удалении последнего ребёнка summary становится незапланированной конечной задачей; не превращать вычисленный интервал в новую самостоятельную работу молча. Структурные изменения и undo также пересчитывают границы и конфликты.

## 9. Результат расчёта и транзакция

```text
ScheduleResult:
  feasibility: feasible | incomplete | infeasible
  originDate: date | null
  projectFinishIndex: integer | null
  coverage: { knownLeafCount, totalLeafCount }
  tasks: { ES, EF, LS, LF, projectFloat, constraintFloat?, blockedReason? }
  criticalTaskIds: []
  criticalDependencyIds: []
  summaries: { start?, finish?, partial, containsCritical }
  diagnostics: [{ code, taskIds, dependencyIds, messageKey }]
```

Чистая детерминированная функция `calculateSchedule(input)`. Нет Date.now, HTTP, SQL, браузера или состояния раскрытия дерева. Проверка → изменение исходных данных → расчёт → сохранение ревизии и результата/диагностик — атомарно. UI получает одну согласованную ревизию; старый сетевой ответ не перезаписывает новый.

Пересчёт после даты, длительности, режима, связи, добавления/удаления, структуры, календаря и начала проекта. Переименование, поиск, сворачивание и перестановка соседних строк не должны менять вычисленные даты. Один drag = одно изменение и одна undo-операция, а не сотни записей по движению мыши.
