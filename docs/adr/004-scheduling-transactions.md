# ADR 004 — расчёт расписания и атомарные команды

Дата: 2026-10-07. Статус: принято для реализации S2 в рамках defaults D04–D12.

## Контекст

S1 хранит дерево и пользовательские даты. S2 должен рассчитывать расписание независимо от React и сохранять исходные данные, зависимости, ревизию и отмену согласованно. Семантика задана в [SCHEDULING](../SCHEDULING.md).

## Решение

- Чистый `calculateSchedule(input)` в domain; отдельные календарные функции. Расчёт использует целые границы рабочих дней, окончания для пользователя включительны. Сводные строки не участвуют в графе работ.
- SQLite migration 002 добавляет календарь/начало проекта, режим/длительность/ограничения задач и таблицу leaf-only FS зависимостей. Старые input dates сохраняются как незапланированные пометки: миграция не превращает ввод в подтверждённый Fixed.
- Команды `project.schedule`, `task.plan`, `dependency.create`, `dependency.delete` используют существующие expectedRevision, operationId и bounded undo. Ответ дерева включает зависимости и рассчитанное расписание. GET schedule возвращает тот же результат с ревизией проекта.
- Результат не кешируется: он рассчитывается в той же SQLite-транзакции, что исходные данные. Это исключает рассогласование algorithmVersion/revision; отдельная таблица результатов пока не нужна.
- Перевод запланированной работы в done фиксирует вычисленный интервал: календарные даты при известном начале проекта, относительные индексы иначе. Отдельные поля completedStart/Finish и completedStartIndex/FinishIndex сохраняют исходный planMode и notBefore. Возврат из done явной командой статуса снимает фиксацию. Планирование done требует предварительного возврата из done.
- При превращении запланированной или связанной конечной работы в родителя `preserveWork` обязателен: собственная работа и все её связи переходят новому work-child в одной транзакции. Клиент и сервер используют общий чистый predicate для подтверждения, включая undated done и явный deadline; вычисления расписания остаются в domain на сервере. Удаление последнего ребёнка оставляет незапланированную конечную задачу.
- Некорректный граф (цикл, self-link, дубликат, чужая или сводная вершина) отклоняется до commit. Противоречие корректных пользовательских ограничений сохраняется атомарно с `infeasible` и диагностикой; обычный критический путь такого проекта отсутствует. Выходные для новых Fixed границ отклоняются.
- Изменение дат через старый `task.update` сохраняет пометки только у unscheduled. Для запланированных работ режим и источники дат меняются явной командой `task.plan`; React не изобретает правила расчёта.
- Пропущенный `deadline` сохраняет прежнее требование; явный `null` очищает его. Повторный Auto plan без `notBefore` сохраняет прежнее ограничение этого режима. Лимит 1 000 000 рабочих дней относится к вводимой Auto-длительности; производная Fixed-длительность допускает весь поддерживаемый диапазон календарных дат.

## Последствия

Существующие проекты и auth/session данные сохраняются. Старые operation responses и undo snapshots очищаются при migration 002, поскольку их формат предшествует scheduling contract; сохранение undo после перезапуска не гарантируется D11. Новые зависимости и настройки входят в undo и restart tests. Гант и редактирование расписания в панели остаются S3; S2 доступен через серверный API.

Полный пересчёт проекта проще инкрементального и предпочтителен для первого релиза. Миграция проверяется только на синтетической БД; production runtime не открывается.
