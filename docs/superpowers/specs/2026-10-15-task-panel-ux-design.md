# Карточка задачи — компактный интерфейс и согласованное сохранение

Дата: 2026-10-15. Статус: спецификация подготовлена по поручению владельца; реализация не начата. ID: `task-panel-ux`. Новые детали компоновки и поведения ниже — рабочий D22, а не отдельные подтверждённые C-решения. По поручению владельца 2026-10-16 подготовлен [план реализации](../plans/2026-10-16-task-panel-ux.md) для независимого ревью. Реализация требует отдельного поручения; рабочий статус D22 сохраняется.

Основание: внешнее предложение по упрощению карточки от 15.10.2026 и существующие правила leaf. Исходный документ, его скриншоты и примеры пользовательских задач в репозиторий не переносятся. Единственные утверждённые визуальные референсы — три PNG из [design/README.md](../../../design/README.md). Исключённый коллаж подзадач не используется. Описание новой компоновки не становится четвёртым утверждённым визуальным референсом.

## 1. Цель и границы

После открытия карточки пользователь сразу видит название, статус и реальные сроки, может дополнить описание, добавить подзадачу, открыть зависимости или журнал. Сохранение доступно независимо от положения прокрутки. Вторичные операции не повторяются в содержимом вкладок.

В объём входят компактная правая панель, три вкладки, единый редактор сроков, меню действий, управление черновиком, локальные ошибки, фокус и адаптивность панели. Используются существующие API и модель данных. Новые поля задачи, миграции, типы зависимостей, библиотеки, автосохранение, автопланирование и изменения формул scheduler/CPM не входят в задачу. Если реализация потребует расширения общего контракта, сначала отдельно обосновать его и ADR; цепочку независимых записей нельзя выдавать за атомарную команду.

Главный экран, строки дерева/Ганта и проектный журнал сохраняют свои правила. Переработка общей мобильной шапки приложения не входит в объём; сама карточка не должна увеличивать ширину документа.

## 3. Каркас панели

### 3.1. Постоянные зоны

Панель открывается справа поверх правой части рабочего пространства и сохраняет контекст дерева/Ганта. Переход к другой задаче заменяет содержимое одной панели, не открывает второй sidebar.

Сверху вниз:

1. Компактный путь проекта/родителей, возврат при переходе из дочерней/связанной задачи, меню `⋯`, закрытие.
2. Единственный редактируемый заголовок задачи.
3. Компактные кнопки статуса и сроков.
4. Вкладки **«Задача / Зависимости / Журнал»**.
5. Прокручиваемое содержимое активной вкладки.
6. Закреплённая зона состояния и сохранения задачи.

Зоны 1–4 и 6 находятся вне основной прокрутки. Вкладка имеет один основной вертикальный scroll-container. Описание и дерево подзадач не получают собственных вложенных вертикальных скроллов. Меню, календарь и результаты поиска могут прокручиваться внутри ограниченного popover; это временные редакторы, а не второй постоянный скролл карточки. Большое содержимое журнала использует ту же основную область панели; не оставлять одновременно скроллы оболочки, composer и ленты при штатной высоте.

Открытие popover/меню не меняет размеры панели и не сдвигает поля. Нижняя зона резервирует высоту под состояние и действия, даже когда кнопок нет. Ошибка у поля может увеличить содержимое; основной scroll доводит поле до видимой области, шапка и вкладки остаются на месте. На очень низком экране доступность полей и действий важнее фиксированной геометрии: временный редактор допускает собственную прокрутку.

### 3.2. Геометрия и визуальный стиль

Рабочий ориентир для desktop — ширина около 480 CSS px, проверяемый диапазон 420–520 px. Это D22, а не утверждённые пиксельные размеры. На 1440×900 и 1280×800 проверять панель в составе всего рабочего пространства: дерево остаётся доступным, а оставшаяся часть Ганта сохраняет читаемый контекст. Ширину 560–640 px из внешнего предложения автоматически не принимать.

При ширине viewport менее 900 px рабочий default — одна полноэкранная карточка с возвратом к исходному экрану без потери его состояния. При 375×812 панель и её обычные контролы не создают горизонтальную прокрутку документа; локальная горизонтальная прокрутка очень глубокого дерева допустима по существующим правилам. При увеличении масштаба содержимое остаётся доступным, кнопки не обрезаются; не ограничивать заголовок фиксированной высотой.

Белая поверхность, тонкие разделители, спокойные вторичные подписи. Зелёный акцент — активное действие/выбранный элемент; красный — ошибка/удаление. Критичность и статус различаются по смыслу и подписям. Обычный текст описания и записи журнала не обводятся рамками полей до редактирования. Использовать существующие токены, локальные иконки и шрифты без CDN. Размеры контролов и контраст проверяются вместе с видимым клавиатурным фокусом.

## 4. Шапка, название и статус

Название показывается один раз как заголовок. Клик или клавиатурная активация открывает редактирование на том же месте; пустое название получает локальную ошибку. Завершение ввода оставляет значение в общем черновике, не отправляет отдельную запись. Длинное название переносится; полный текст доступен в редакторе. Escape отменяет текущую сессию редактирования названия до её исходного значения, не сбрасывая остальные поля и не закрывая панель.

Статус имеет подпись текущего значения и сохраняет существующие `todo / doing / done`. Выбор меняет общий черновик. Правила завершённой работы и явного возврата в работу сохраняются; UI не разблокирует даты только за счёт смены вкладки. Редактирование заголовка/статуса в любой вкладке отражается в одном черновике.

Путь родителей компактен; полный путь доступен при раскрытии/фокусе. Переход по пути разрешается через ту же защиту несохранённых изменений, что и выбор другой задачи.

## 5. Вкладка «Задача»

### 5.1. Описание

Пустое описание показывает действие «Добавить описание». Непустое — plain text с сохранением переносов и доступным действием редактирования. Рабочий default для длинного текста — до четырёх строк в свёрнутом состоянии и «Развернуть»; раскрытый редактор растёт в общей области прокрутки, не прячет ввод внутри фиксированной textarea со вторым scroll при обычном объёме текста.

Разворачивание/сворачивание сохраняет текст и не записывает задачу. Смена вкладки не уничтожает незавершённое редактирование. HTML не исполняется; rich text, вложения, метки, приоритеты и исполнители не добавляются.

### 5.2. Подзадачи

Под описанием — заголовок «Подзадачи» и полная ветка на общем TaskTree независимо от основного поиска. Сохраняются произвольная глубина, раскрытие, относительные отступы, текущие статусы/даты и C30/C31. Если показан счётчик, он обозначает число непосредственных подзадач, а не число видимых строк или всех потомков. Для пустой ветки достаточно одной краткой строки с действием добавления.

Одна точка добавления верхнего уровня секции открывает существующий быстрый ввод под выбранной задачей. Когда он открыт, отдельная дублирующая кнопка исчезает с сохранением понятного места ввода. Иконки дочерних строк и клавиатурные команды задают контекст по существующим правилам; нажатие строки само по себе не переносит основной composer проекта.

Название и один Enter/кнопка подтверждения создают подзадачу. Родитель уже выбран, повторного select нет. Сроки и предшественники доступны компактными контролами существующего QuickAdd: даты пусты, очищаемая длительность 1, условный preview по C19/C21. Tab/Shift+Tab меняют уровень только внутри редактора названия и не выходят за выбранную ветку; в остальных полях это обычная навигация. Черновики основного дерева и каждой ветки панели раздельны.

Создание подзадачи — отдельная плановая команда. При dirty-черновике самой задачи ввод и его текст сохраняются, отправка блокируется с точным пояснением «Сначала сохраните изменения задачи». Не создавать подзадачу скрытым предварительным сохранением. Преобразование конечной работы в сводную сохраняет действующую проверку/подтверждение `preserveWork`; нельзя потерять её собственную работу и связи.

Переход к ребёнку заменяет панель; возврат восстанавливает вкладку «Задача», раскрытие, scroll и фокус на исходной строке, при её исчезновении — на доступном вводе/заголовке секции. Escape из QuickAdd обрабатывается существующим редактором и не закрывает всю панель; непустой текст не теряется молча.

Повторных блоков зависимостей, переноса и удаления под секцией нет.

## 6. Единый редактор сроков

### 6.1. Подпись и открытие

Кнопка в шапке отражает только реальные исходные поля конечной работы:

| Состояние | Пример подписи |
| --- | --- |
| Все поля пусты | «Без дат» |
| Только длительность | «Без дат · 3 раб. дня» |
| Только начало | «Начало: 19 окт.» |
| Только окончание | «Окончание: 23 окт.» |
| Одна дата и длительность при сохраняющемся неполном интервале | Подпись имеющейся даты и заданной длительности |
| Полный интервал | «19–23 окт.»; заданная длительность добавляется при её наличии |

Примеры иллюстрируют формат, не выводят duration из условной полосы. Если duration=null, не выдавать вычисленный span за заданную длительность. Полные даты с годом доступны в редакторе и доступном описании; однодневный интервал можно показать одной датой.

Для summary показываются только допустимые вычисляемые сводные сроки, без редактора собственной длительности. При неполном сводном интервале — «Сводные сроки не определены» и краткое пояснение по запросу; частичный диапазон не подставляется. Для done/удалённой/заблокированной задачи сохраняются действующие ограничения с доступной причиной.

На desktop кнопка открывает popover поверх панели, на узком экране — доступный редактор в пределах viewport. Внутри находятся начало, окончание, длительность и единицы календаря проекта. Даты доступны через календарь и клавиатурный ввод DD.MM.YYYY.

### 6.2. Редактирование и закрытие

Все три поля необязательны. Использовать C18 и действующий общий helper: начало сохраняет длительность; окончание сохраняет начало; длительность использует известную дату. Пересчёт выполняется после завершения ввода, а не на каждой неполной цифре. Очистка отдельного поля оставляет его пустым по C18; очистка не заполняет его из Ганта, родителя или сегодня.

Действия «Сегодня»/«Завтра» применяют существующий календарный helper к началу в timezone проекта, а не тихо назначают даты при открытии. Недопустимый день объясняется по текущему календарю, без нового скрытого snapping. Есть очистка отдельных полей и явное «Очистить все сроки» (начало, окончание, длительность). Не использовать неоднозначное действие «Без дат», которое могло бы означать как удаление двух дат, так и удаление длительности.

Редактор сразу меняет общий черновик задачи. «Готово» завершает активный ввод, выполняет проверку и закрывает редактор при валидных значениях; оно не записывает на сервер. Escape/внешний клик закрывают редактор с сохранением уже введённого черновика, включая ошибочное значение; при следующем открытии оно доступно для исправления. Escape из вложенного календаря сначала закрывает календарь. Полная запись выполняется только нижней кнопкой «Сохранить»; вторую кнопку «Применить» не добавлять.

Ошибка связана с конкретным полем: неверный формат, невозможная дата, нерабочий день или недопустимый интервал. Общего «Проверьте даты» недостаточно. После серверного отказа исходный ввод сохраняется. Если ошибка в закрытом редакторе, нижняя зона даёт действие «Исправить сроки», открывающее его с фокусом на проблемном поле.

Условные значения C19/C25 не заполняют source-поля и не участвуют в summary/CPM. Кнопка не обещает условную дату как реальную.

## 7. Вкладка «Зависимости»

### 7.1. Граф и ввод

Сохранить утверждённую вертикальную схему: непосредственные предшественники сверху, текущая задача в центре, последователи снизу. Каждое ребро соединяет собственные реальные endpoints; независимые предшественники не рисуются последовательной цепочкой. Критичность и резервы приходят с сервера, со специальными подписями partial/infeasible.

У группы предшественников — действие «Добавить предшественника», у последователей — «Добавить последователя». Каждое открывает один searchable picker сразу с известным направлением. Отдельных select направления и списка задач под поиском нет. Кандидаты исключают self, дубли, summary, другой проект и цикл; сервер повторяет проверку. Пустые результаты поиска отличаются от отсутствия допустимых задач и ошибки загрузки.

Если задача сводная, показывать существующее ограничение leaf-only и переход к её конечным работам; не предлагать неработающие действия добавления. Родство не создаёт зависимости.

### 7.2. Граница атомарности

| Действие | Черновик и запись |
| --- | --- |
| Добавить/удалить входящего предшественника текущей задачи | Меняет `predecessorIds` общего черновика; нижнее «Сохранить» отправляет одну task.edit вместе с остальными полями |
| Добавить последователя или удалить исходящую связь | Отдельная существующая dependency.create/delete после подтверждения выбора; доступна только при чистом черновике задачи |
| Перейти к соседней задаче | Навигация с защитой несохранённых изменений |
| «Показать на Ганте» | Навигация к сохранённым данным без записи; при dirty/неопределённом исходе действует защита, черновик не сбрасывается |

Текущий контракт task.edit заменяет только входящие endpoints. Не расширять его исходящими связями и не отправлять несколько команд под одним обещанием «Сохранить всё». При dirty-черновике исходящее действие объясняет: «Сначала сохраните изменения задачи». Пользователь сохраняет задачу и затем явно выполняет отдельное действие; скрытой очереди команд нет.

Несохранённые входящие изменения показываются в схеме с подписью «Не сохранено», удаляемое ребро — как ожидающее удаления с возможностью восстановить. Это черновой слой схемы, не подтверждённая связь и не результат scheduler. Счётчик вкладки отражает сохранённые непосредственные связи; наличие draft-изменений обозначается отдельным доступным маркером.

После ack task.edit принять канонические даты и связи сервера, включая necessary push C25, обновить clean baseline только отправленного черновика. Одна команда — один revision/Undo. Ошибка в любом поле/связи откатывает всю команду; неполные source-даты остаются неполными. При отдельной исходящей операции те же каскад/rollback/retry/Undo выполняет сервер.

Frozen outcome при exact retry подтверждает исходную операцию, но не разрешает понизить уже известную revision или заменить более новое дерево историческим ответом. Разрешение pending и чтение актуального состояния сохраняют действующий контракт; более новый локальный draft не помечается сохранённым старым ack.

### 7.3. Расчёт

Под схемой — сворачиваемый блок расчёта с раздельными резервами проекта/текущего размещения и существующими подписями C16. Отсутствие дат само по себе не предупреждение. Ошибку, мешающую сохранению, показывать вне свёрнутого блока.

При dirty-изменении сроков/статуса/входящих связей результаты помечаются «По сохранённому плану». Нельзя выдавать прежнюю критичность за пересчёт черновика или запускать собственный scheduler в React. Серверный анализ после подтверждённой записи обновляет схему, дерево и Гант согласованно.

## 8. Вкладка «Журнал»

Сохраняется компактный composer: поле текста, редактируемая календарная дата, «Сохранить запись» после появления ввода и «Очистить черновик» при изменённом черновике. Начальная дата — сегодня в timezone проекта; явно изменённую/очищенную дату не заменять при смене суток. Пустая форма не показывает набор disabled-кнопок.

Лента — существующие компактные строки по дням без рамок-карточек, с меню записи `⋯` и постепенной загрузкой. Не добавлять время записи, total count из неполных pages или постоянную подпись про Undo. На вкладке показаны прямые записи задачи, не агрегат потомков.

Журнал работает при обычном dirty-черновике задачи и не сохраняет/сбрасывает его. Поля задачи и запись журнала имеют разные кнопки, разные статусы и отдельные revision/envelope. Независимость не отменяет запрет конкурирующих writes при pending/uncertain, закреплённый в спецификации журнала.

Различать:

- запись подтверждена, список обновлён — короткое «Запись сохранена» у composer;
- запись подтверждена, GET списка завершился ошибкой — «Запись сохранена. Не удалось обновить историю» и повтор чтения в области ленты; повтор не создаёт запись ещё раз;
- первоначальная загрузка не удалась — локальная ошибка ленты с повтором, без утверждения о результате несуществующей записи;
- результат отправки неизвестен — «Не удалось подтвердить сохранение» и exact retry; обычный новый submit недоступен;
- отказ валидации/конфликт — текст и дата остаются, действуют pinned baseline и явное разрешение конфликта.

Согласование page/tree metadata по D21 не продвигает dirty planning baseline. На вкладке журнала название/путь берутся из согласованного journal metadata; если они отличаются от локального заголовка-черновика, компактно обозначить несохранённое название задачи и не подменять им сохранённые метаданные записи. Никаких текстов в localStorage/sessionStorage, URL, history.state или логах.

## 9. Меню карточки и структурные операции

Общее меню `⋯` содержит «Добавить соседнюю задачу», «Переместить…», «Показать на Ганте», отделённое «Удалить задачу…». Удаление ветки явно сообщает о потомках и записях журнала, сохраняет существующие правила plan Undo. Меню строки дерева по C30 не возвращается.

«Переместить…» открывает один диалог поиска нового родителя с путём и явным пунктом «В корень». Текущая задача и её потомки не выбираются. Внутри диалога сворачиваемый раздел «Порядок и уровень» сохраняет существующие команды «Выше», «Ниже», «На уровень выше», «Вложить в предыдущую задачу» с их валидаторами и причинами недоступности. Эти операции используют существующие команды, не создают дополнительные поля модели и не занимают блок в каждой вкладке. Действующие клавиатурные команды основного дерева сохраняются; новые глобальные сочетания не вводятся.

Диалог перемещения проверяет существующие ограничения до подтверждения и объясняет недоступность. Dirty/pending/uncertain task draft не обходится структурной командой. Перемещение, удаление и преобразование leaf→summary не выполняются скрытым побочным эффектом открытия меню. Отмена диалога ничего не меняет.

## 10. Черновики, сохранение и навигация

### 10.1. Единый черновик задачи

Один task draft содержит название, статус, описание, nullable source-поля и входящие `predecessorIds`. Его владельцем остаётся панель/существующий контроллер задачи; вкладки и popover не имеют независимых серверных записей этих полей. Переключение вкладки и закрытие локального редактора не сбрасывают значения или baseline. Dirty определяется всем набором, включая связи и очищенные поля.

QuickAdd и journal drafts сохраняют отдельные ключи проекта/задачи, свой lifecycle и RAM-изоляцию. Ни один поздний ответ не очищает другой черновик. Обычный background GET не заменяет dirty task draft и его исходную revision. После 401/завершённого logout приватное RAM-состояние очищается по действующим правилам; refresh страницы не обещает сохранность ввода.

### 10.2. Нижняя зона

| Состояние задачи | Представление и действие |
| --- | --- |
| Clean | Нет постоянного «Всё сохранено», активных кнопок сохранения/сброса нет; место зоны сохранено |
| Dirty, валидный | «Есть изменения», «Сбросить изменения», «Сохранить» |
| Dirty, невалидный | Краткая причина, «Исправить…», «Сбросить изменения»; Save недоступен с доступной причиной |
| Saving | «Сохраняем…», повтор и конкурирующие записи недоступны |
| Подтверждённый успех | Короткое подтверждение только после ack; затем clean; если появился новый черновик, он остаётся dirty |
| Определённый отказ | Понятная ошибка у операции/поля; draft сохранён, повтор после исправления |
| Stale revision | «Задача изменилась»; показать актуальные данные для явного разрешения, не overwrite и не silent rebase |
| Uncertain | «Не удалось подтвердить сохранение», exact retry неизменного envelope/operationId; сброс, закрытие и competing writes блокируются до определённого результата |
| Задача удалена | Сообщение об удалении, черновой текст доступен для копирования; запись не переназначается другому ID |

«Сбросить изменения» возвращает весь task draft к его сохранённому baseline, включая source и связи, но не стирает QuickAdd/journal drafts. Название не конфликтует с общей командой «Отменить изменение плана». Footer остаётся доступен во всех вкладках; на «Журнале» его статус явно относится к задаче и не заменяет статус записи.

### 10.3. Закрытие и выбор другой задачи

Для обычного dirty task draft показывается один диалог: «Сохранить», «Не сохранять», «Продолжить редактирование». «Сохранить» выполняет одну task.edit и продолжает исходную навигацию только после подтверждённого успеха. При ошибке/uncertain панель и значения остаются. «Не сохранять» сбрасывает только task draft и выполняет выбранный переход; самостоятельные QuickAdd/journal drafts подчиняются своим существующим RAM guards. Смена вкладки внутри той же задачи такого диалога не требует.

При невалидном draft действие сохранения объясняет ошибку и возвращает к полю, а «Не сохранять»/продолжение остаются доступны. Pending/uncertain нельзя обходить выбором «Не сохранять». Browser Back/Forward, путь родителей, переход к соседу и смена проекта применяют одну защиту. Явное закрытие панели с обычным journal draft может сохранять его в RAM; выход из сессии/страницы использует действующие guards предупреждения о потере.

### 10.4. Совместимость навигации

Сохранить разбор существующих URL/history `panel=details|subtasks|dependencies|journal` без router dependency. `details` открывает «Задача»; `subtasks` открывает ту же вкладку с видимой секцией подзадач. Новые переходы могут сохранять эти внутренние значения для выбора секции; отдельной четвёртой видимой вкладки нет. `dependencies` и `journal` сохраняют смысл. Адрес не содержит текстов, дат черновика или credentials.

Переходы и возврат сохраняют выделение, раскрытие, фильтры, масштаб, период и обе оси прокрутки underlying дерева/Ганта, а также позицию проектной ленты по D21. Устаревший async restore не забирает фокус после самостоятельной навигации пользователя.

## 11. Клавиатура и доступность

Вкладки используют tablist/tabpanel, ArrowLeft/Right/Home/End и видимое активное состояние. Tab в полях — обычная навигация, кроме явно активного редактора названия QuickAdd. Кнопки и редактируемый заголовок имеют доступные имена, состояния expanded/disabled и связанные ошибки; причина недоступности читается без hover.

Escape сначала обрабатывает ближайший календарь, picker, меню или редактор. Он не закрывает их вместе с панелью. После закрытия popover фокус возвращается на его кнопку; после меню/диалога — на trigger или ближайшее сохранившееся действие. Закрытие карточки возвращает фокус к исходной строке/ссылке, при исчезновении — к доступному контролу исходного экрана. Диалоги подтверждения и перемещения доступны с клавиатуры и удерживают фокус; обычный desktop sidebar и немодальные popover не получают лишней ловушки фокуса.

Enter в описании/журнале остаётся переносом строки. Ctrl/Cmd+Enter в журнале использует существующий submit. Ctrl/Cmd+Z внутри текстового поля отменяет текст, за его пределами действует существующий Undo плана с его guards. Цвет дополняется текстом/иконкой, ошибки — aria-describedby/alert, статусы — умеренным live-region без повторного объявления всей панели.

## 12. Затрагиваемые компоненты и порядок работы

Использовать существующие TaskPanel, PlanFields, Dependencies/PredecessorPicker, TaskTree/QuickAdd, TaskJournal/JournalEditor/JournalFeed, ActionMenu и контроллеры черновиков/навигации. Новые локальные компоненты допустимы для шапки, редактора сроков и footer, если это уменьшает ответственность TaskPanel. Не создавать второй источник task draft, собственный scheduler, framework состояния или graph editor.

Порядок будущей реализации: каркас/прокрутка и footer → меню и объединение основной вкладки → редактор сроков → перенос входящих связей и упрощение picker → точные состояния журнала → навигация, адаптивность и приёмка. Это последовательность частей дизайна, не готовый implementation plan. После каждого переноса сохранять существующие проверки атомарности и черновиков; полировка клавиатуры/ошибок проверяется вместе с соответствующим контролом.

Перед реализацией проверить эту спецификацию, затем подготовить план. Макеты и будущие screenshots создаются только на синтетическом проекте. Новые изображения не включаются в публичный пакет без отдельного privacy review. Составление спецификации не завершает S4–S6, не разрешает production-доступ, push, публикацию или deployment.
