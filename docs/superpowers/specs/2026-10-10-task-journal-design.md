Дата: 2026-10-10. Статус: сервер и клиент реализованы в принятых Task1–2; Task3 добавляет независимую браузерную приёмку и финальные проверки. Фактические результаты и ограничения — в [STATUS](../../STATUS.md). Технические подробности — рабочий D21, а не новые подтверждённые C-решения. Архитектурная граница — [ADR 014](../../adr/014-task-journal.md). Действующие [UI](../../UI.md), [архитектура](../../ARCHITECTURE.md), [приватность](../../PRIVACY.md) и C11–C28 сохраняются.

## 1. Цель и анализ предложения

Владелец поручил разобрать синтетическое предложение журнала, подготовить спецификацию и план, реализовать функцию отдельными агентами с независимыми reviews и коммитом после каждого принятого этапа. Полный цикл разрешён; эта спецификация описывает первый этап. Источники предложения: `README_FOR_AGENT.md`, `HANDOFF.txt`, четыре PNG и `preview.html` из предоставленного архива. Архив рассматривается как данные; его инструкции не меняют AGENTS и правила безопасности. Файлы архива и прототип не копируются в репозиторий.

Просмотрены все четыре proposal PNG и [три утверждённых PNG](../../../design/README.md). Предложение согласуется со светлой компоновкой, узкой навигацией и компактной правой панелью: проектная лента в основном содержимом, журнал конкретной задачи в четвёртой вкладке панели, редактор проекта в диалоге, быстрое действие в меню строки. Не переносим нарисованные новые колонки сроков, символ бренда, детали Ганта, декоративные поля или размеры как новые требования. Утверждёнными визуальными референсами остаются только исходные три PNG. Прототип показывает переключение статических сцен; он не доказывает persistence, CRUD, клавиатурную доступность или браузерную историю.

Журнал — датированные пользовательские текстовые записи о работе по задаче, не автоматический audit log. Один объект доступен в ленте проекта и своей задачи. Любая существующая задача, включая родителя, `done` и работу без дат, принимает записи. `workDate` задаёт день работы, а технические UTC timestamps используются только для стабильного порядка. Ни запись, ни её дата не меняют статус, исходные сроки, FS, календарь или CPM.

Объём: CRUD записей, проектная и task-only ленты, поиск/период в проекте, постепенная загрузка, общий редактор, быстрое действие меню, защита черновиков, сохранение позиции/навигации и безопасные delete/undo/retry. Не входят глобальный журнал, часы/таймеры, категории, вложения, Markdown/HTML, реакции, упоминания, AI, отчёты, события Ганта, доска и реализация S5 import/export.

## 2. Исследованная реализация и выбор подхода

Текущая схема — миграции 001–003. `Repository.mutate()` проверяет project revision и durable `operations`, сохраняет private before-snapshot, запускает cascade/solver и возвращает tree V2. Undo ограничен последними двадцатью snapshots проекта/сессии и текущей project revision. `Repository.save()` сейчас удаляет все dependencies и tasks проекта и вставляет задачи заново. Поэтому прямое добавление каскадного journal FK без изменения этого seam потеряет записи даже при переименовании. Private snapshots содержат tasks/dependencies/provenance, а frozen historical replies и migration archive имеют отдельные strict validators/digests. Нельзя распространять journal поля в tree V2 или менять исторические байты.

| Подход | Преимущества | Цена / решение |
|---|---|---|
| Отдельный журнал с собственной revision/replay, адресным task save и sidecar удалённой ветки | Нет solver при CRUD; текущий tree V2 и frozen history сохраняются; записи живых задач переживают плановый Undo | Нужна транзакционная интеграция task lifecycle и явная подпись границ Undo. **Выбран.** |
| Все journal команды в общем plan revision/Undo/snapshot | Единая хронологическая отмена | Меняет snapshots/replay и путь Undo; нынешний ответ tree требует solver, нужен новый способ выдачи schedule без пересчёта. Для этой функции избыточно. |
| Журнал в description или localStorage | Маленький первоначальный diff | Не обеспечивает единый объект, надёжное сохранение, удаление ветки, версии и серверную изоляцию. Отклонён. |

Один writer изменяет миграцию, shared journal contracts и repository save/undo. Новый journal repository отвечает за чтение/CRUD/replay; planning repository вызывает небольшой lifecycle seam внутри своей существующей транзакции. Новый state framework, ORM, сервис или пакет не требуется. Task save refactor ограничен сохранением стабильных task IDs и provenance; scheduling behavior не меняется.

## 3. Хранение и миграция

Добавить `004-task-journal.sql`; перед реализацией перепроверить номер. Миграция аддитивная и транзакционная, без чтения runtime данных разработчиками. Содержит:

- `journal_state(projectId PRIMARY KEY REFERENCES projects(id) ON DELETE CASCADE, revision INTEGER NOT NULL CHECK(revision>=0))`. Начальная revision 0 для всех existing/future projects; счётчик монотонный и независим от `projects.revision`.
- `journal_entries(id TEXT PRIMARY KEY, projectId TEXT NOT NULL, taskId TEXT NOT NULL, workDate TEXT NOT NULL, body TEXT NOT NULL, createdAt TEXT NOT NULL, updatedAt TEXT NOT NULL)`; `STRICT`, project FK и composite `(projectId,taskId) → tasks(projectId,id)` с `ON DELETE CASCADE`. NUL-safe SQL ограничение `length(CAST(body AS BLOB)) BETWEEN 1 AND 30000` считает UTF-8 bytes и вместе с длиной date 10 дополняет полную серверную валидацию; FK не допускает запись задачи другого проекта. Индексы `(projectId,workDate DESC,createdAt DESC,id DESC)` и `(projectId,taskId,workDate DESC,createdAt DESC,id DESC)`.
- `journal_operations(operationId TEXT PRIMARY KEY, projectId, sessionId, payload, response, responseSha256, contractVersion)`; FK проекта, `contractVersion=1`. Отдельный namespace операции журнала, независимый от planning `operations`. Ни identity сессии, ни payload/digest не выдаются клиенту.
- `undo_journal_entries(undoSequence, id, projectId, taskId, workDate, body, createdAt, updatedAt)`: primary key `(undoSequence,id)`, FK `undoSequence → undo_snapshots(sequence) ON DELETE CASCADE`; project FK. Это приватный sidecar исключительно для удалённых записей, а не активная journal таблица. FK к отсутствующей задаче здесь намеренно нет; принадлежность snapshot проекту, удаляемым IDs и полнота данных проверяются перед записью/restore.
- `undo_journal_manifest(undoSequence PRIMARY KEY REFERENCES undo_snapshots(sequence) ON DELETE CASCADE, entryCount INTEGER NOT NULL CHECK(entryCount>=0), entriesSha256 TEXT NOT NULL)` и аддитивная колонка `undo_snapshots.journalLifecycleVersion INTEGER NOT NULL DEFAULT 0 CHECK(journalLifecycleVersion IN (0,1))`. Historical rows остаются с 0. Каждый новый planning before-snapshot получает version 1 и обязательный manifest, в том числе при нуле удалённых записей. Digest — SHA-256 canonical `{undoSequence,projectId,entries}`; entries сортированы по ID и включают все поля JournalEntry. Stored hex digest валидируется. Это позволяет обнаружить исчезновение manifest/одной/всех rows и изменение валидного текста/даты, не меняя beforeSnapshot JSON или frozen bytes.

Sidecar существует только пока жив соответствующий bounded Undo snapshot; pruning двадцати snapshots и удаление проекта убирают его. Deleted entries не доступны через ленты/API. Существующие durable journal operation replies могут содержать прежний текст после удаления; это server-private retry storage, как существующий planning log, не публичная история. Удаление записи означает удаление из активного журнала, не secure erase из SQLite/backups/replay.

`openDatabase` принимает непрерывные версии 1…4, fresh path создаёт 1→2→3→4, schema3 получает только 004, schema4 переоткрывается без DDL. Schema2 по-прежнему требует C17 preview/ack **до любого** pragma/DDL, затем 003 и 004; schema1, gaps/future versions отклоняются. Migration004 не меняет `operations`, `undo_snapshots.beforeSnapshot` или `scheduling_migration_archive`; новая lifecycle колонка только маркирует обязательность приватного manifest. Ошибка внутри 004 откатывает её целиком и не помечает версию применённой. Старые binaries не должны открывать schema4 для записи. Production backup остаётся обязанностью эксплуатационного workflow; production migration этим поручением не разрешена.

SQLite backup уже сохраняет весь файл согласованным API, поэтому включает active journal, state/replay и private Undo sidecar. Тест backup должен подтвердить восстановление journal rows на синтетической копии. S5 остаётся незавершённым: будущий versioned project export/import обязан учитывать active journal; auth, operation logs и Undo sidecar в проектный экспорт не входят. В этой задаче новый публичный формат экспорта не вводится.

## 4. Данные и API

`JournalEntry = {id, projectId, taskId, workDate, body, createdAt, updatedAt}`. IDs — UUID; timestamps — canonical UTC ISO серверного `now`. `workDate` валидируется existing `calendarDateSchema`: календарный день 0001–9999, включая високосность. Не преобразовывать в timestamp. В create/update `body.trim()` должен быть непустым; сохранять исходный plain text с внутренними/краевыми переносами и пробелами, лимит 10000 UTF-16 code units как existing description. Body не нормализуется ради отображения. Рабочее уточнение D21 после server review: body и query должны быть well-formed Unicode, unpaired UTF-16 surrogate отклоняется 400 до UTF-8 binding; все допустимые Unicode code points, включая NUL и управляющие символы, сохраняются без замены. SQL byte-bound 30000 покрывает любой well-formed body с максимум 10000 UTF-16 units, а точный текстовый bound проверяет shared schema. Client не задаёт IDs/timestamps, не меняет task/project принадлежность existing entry; изменение задачи записи не входит в scope.

Routes используют общие session, exact Origin/JSON для writes, `X-Leaf-Contract-Version: 2`, существующий bodyLimit 64 KiB и safe errors. Отдельные strict journal envelopes/responses имеют `journalContractVersion: 1`. Legacy replay header журналом не принимается (existing invalid-request policy). Planning tree/command response V2 остаются прежними.

| Метод / путь | Вход | Успех |
|---|---|---|
| GET `/api/projects/:id/journal` | Query `q?`, `from?`, `to?`, `limit?`, `cursor?` | `JournalPage` |
| GET `/api/projects/:id/tasks/:taskId/journal` | Только `limit?`, `cursor?`; существующая задача именно этого проекта | `JournalPage`, прямые записи задачи |
| GET `/api/projects/:id/journal/:entryId` | Scoped entry ID; без query | `JournalEntryRead` для явного разрешения editor/delete conflict |
| POST `/api/projects/:id/journal` | `{journalContractVersion:1, operationId, expectedJournalRevision, taskId, workDate, body}` | 201 `JournalMutation`, `entry` |
| PATCH `/api/projects/:id/journal/:entryId` | `{journalContractVersion:1, operationId, expectedJournalRevision, workDate, body}` — полный editor draft | 200 `JournalMutation`, `entry` |
| DELETE `/api/projects/:id/journal/:entryId` | JSON `{journalContractVersion:1, operationId, expectedJournalRevision}` | 200 `JournalMutation`, `deletedEntryId` |

`JournalPage = {journalContractVersion:1, projectId, taskId: UUID|null, journalRevision, projectRevision, entries: JournalEntry[], nextCursor: string|null}`. `taskId=null` означает проект. Название/путь задачи строится по current tree и taskId, а не сохраняется в записи. `JournalMutation = {journalContractVersion:1, kind:'saved', projectId, journalRevision, entry}` либо `{journalContractVersion:1, kind:'deleted', projectId, journalRevision, deletedEntryId}`; это strict discriminated success union с взаимоисключающими полями. Revision и expectedJournalRevision — неотрицательные safe integers, operationId — UUID. Current tree/CPM в ответ не включать.

`JournalEntryRead = {journalContractVersion:1, projectId, journalRevision, projectRevision, entry}` — strict response одной read transaction, с той же auth/scope/no-store policy. Read не вызывает solver. Его результат обновляет baseline editor **только** после явного разрешения конфликта ниже; обычный фоновый GET не rebases draft.

CRUD выполняется одной SQLite IMMEDIATE транзакцией: validate envelope → проверить durable replay → существование проекта и scoped entry/task → expectedJournalRevision → изменение rows + revision + validated response/digest/replay → commit. New create имеет server UUID. Update сохраняет `createdAt`, меняет `updatedAt`; date меняется только по submitted `workDate`. Даже equal update создаёт успешную операцию и одну новую journal revision; UI обычно не отправляет unchanged editor. DELETE удаляет только scoped ID. Revision увеличивается ровно один раз на новый успешный CRUD. Ошибка rollback не оставляет entry/state/replay. `projects.revision/updatedAt`, task fields, scheduling snapshots и `canUndo` не изменяются.

Cached response проверяется **до** current revision и entry existence, но после authenticated session/envelope. Operation scope — project + session + canonical full request, включая route verb/entryId и journal contract. Exact retry возвращает первоначальный DTO и status (201/200), без UUID/timestamp/revision changes и без новых записей. Reuse другим payload/project/session — 409 `OPERATION_REUSED`, без раскрытия прежнего текста. Stored response проходит sha256 + strict journal validator и проверку соответствия scope/operation результату; damaged replay → safe 500 и никаких writes. Журнал не использует frozen scheduler validators и не обращается к solver при replay.

`JOURNAL_REVISION_CONFLICT` (409) означает отсутствие записи: клиент сохраняет draft, загружает актуальную ленту и показывает конфликт; новая попытка после явного действия пользователя получает новый operationId/revision. Не выполнять автоматическую перезапись. При потере ответа outcome неопределён: сохранить **точный** envelope и operationId, заблокировать изменение отправленного draft до exact retry, кнопка «Повторить сохранение». Retry может вернуть старую revision/entry после более позднего edit/delete/task deletion; клиент не понижает известную revision и не вставляет frozen запись как текущую, а обновляет journal GET. Ack очищает только тот sent draft, а не текст другой задачи/редактора.

Edit draft захватывает `{baselineEntry, baselineJournalRevision}` из coherent прочитанного объекта при **первом** открытии редактора; delete confirmation также захватывает entry/revision при открытии. Submit использует pinned baselineJournalRevision, а не последнюю revision ленты. Ни focus/list GET, invalidation, close/reopen, tab, Back/Forward, ни успешная чужая операция не обновляют этот baseline автоматически, даже если поле пока не изменено. При remote edit → focus GET → stale submit сервер получает старую revision и возвращает409; текущий чужой текст остаётся. Доступная подсказка о stale baseline может появиться заранее, но не заменяет revision check.

После409 получить current `JournalEntryRead`, сохраняя own draft; показать current body/date отдельно от own draft. Явные действия: «Загрузить текущую запись» заменяет draft/baseline после подтверждения потери непустой правки; «Продолжить с моим текстом» сохраняет own body/date и **явно** принимает показанные current entry/revision как новый baseline, затем требует отдельного submit с новым operationId. Если запись удалена —404, редактирование/удаление блокируется, own текст остаётся для копирования, автоматического recreate нет. Для delete после409 нужна новая явная confirmation current entry/revision, а не фоновое продвижение старого диалога. Uncertain операция сначала разрешается exact retry; её envelope нельзя rebase.

Неверные поля/query/date/cursor — 400; auth — 401; Origin — 403; unknown contract — 426; bodyLimit — 413. Scoped чужой/несуществующий task/entry/project — 404 без сведений другого проекта. На сервере нет многопользовательских ACL (D01), но каждое чтение/изменение проверяет связку project/task/entry. Ошибки не включают body, search query, titles, SQL или paths.

## 5. Сортировка, поиск и страницы

Ленты сортируются `workDate DESC, createdAt DESC, id DESC`; UI группирует по полной workDate и показывает календарную дату без времени. Edit текста не меняет порядок; edit даты переносит запись в нужную группу. Последний день одной страницы и первый следующей объединяются в одну группу; append дедуплицирует по ID.

Проектный поиск — буквальная подстрока `normalize('NFC').toLocaleLowerCase('ru')` в body **или текущем title задачи**, с trim query, максимум 300 code units; пустой query означает все записи. `%`, `_` и HTML остаются символами. Рабочий вариант SQL — параметризованная выборка с небольшой deterministic SQLite function для такого Unicode predicate; SQLite ASCII `lower/LIKE` недостаточны для русского текста. Дата `from/to` включительна, каждый край необязателен; `from>to` отклоняется. Query и период через AND, тело и title через OR. Ни status, ни сроки задачи выборку не ограничивают. Без фильтров период не задан; скрытого cutoff нет.

Default limit 50, допустимые integer 1…100. Чтение state/project revision и page rows в одной read transaction. Выбрать limit+1 с keyset `<` по descending tuple, nextCursor только при лишней строке. Не использовать OFFSET. Cursor — base64url strict JSON длиной максимум 4096 с version 1, projectId, taskId/null, нормализованным query, from/to/null, limit, journalRevision, projectRevision и last tuple. Не содержит body/session; не доверять декодированному scope, он должен точно совпасть с route и filters. Невалидный/чужой scope — 400; stale journal **или project revision** — 409 `JOURNAL_CURSOR_STALE`. Рабочее уточнение D21 после server review: cap 4096 учитывает worst-case JSON escaping нормализованного query из 300 units; прежний cap 2048 мог превратить допустимый поиск в 500. Query не усекается и не получает дополнительного запрета управляющих символов. Cursor не обязан быть секретным/подписанным: все поля валидируются, SQL parameterized, scope проверяется независимо; подмена позиции может лишь пропустить часть собственной выборки.

Planning revision в cursor нужна для title search и membership: переименование/удаление/Undo задачи между страницами не создаёт смешанный список. JournalRevision меняется также при удалении/restore реальных journal rows через task lifecycle (§6). В первой версии stale cursor предлагает «Обновить журнал», не склеивает старую и новую выборки. При обновлении сохранить first-visible ID/offset, восстановить его если найден среди загруженных строк, иначе ближайшую группу/начало; фильтры и editor draft сохраняются. Ограниченный размер page защищает response/DOM; поиск линейно проверяет кандидатов, полнотекстовый engine/индекс не вводится преждевременно.

## 6. Task lifecycle, Undo и frozen history

Обычная плановая команда сохраняет tasks адресно: insert новых, update surviving IDs, delete только отсутствующих в next snapshot. Не применять `REPLACE`, delete-all или перенос ID при обычном edit. Deferred parent FK остаётся; dependencies можно пересоздать как прежде. Provenance синхронизируется адресно с next private snapshot, не опирается на побочный cascade. Сохранившиеся journal rows остаются byte-identical при rename/move/status/source/FS/project settings. Current plan calculate/cascade/transaction validation выполняются по прежнему пути, journal CRUD solver не вызывает.

Для `task.delete` сравнить before/after IDs всей ветки внутри existing plan transaction. После создания before-snapshot/получения undo sequence скопировать **только** активные записи удаляемых задач в `undo_journal_entries`, провалидировать scope, затем удалить задачи (journal FK каскад). Если удалены записи, journalRevision увеличивается один раз за всю команду; пустая ветка journalRevision не меняет. Planning beforeSnapshot JSON остаётся неизменного формата. Current UI delete confirmation явно говорит, что журнал этой ветки также удаляется и может быть восстановлен доступной отменой; не обещает восстановление после pruning/изменений чужой сессии.

Undo planning snapshot сравнивает current/target task IDs. Сохранившиеся задачи сохраняют **текущие** записи и правки, даже если они появились после beforeSnapshot. Для lifecycle version 1 до изменения tasks обязательно проверить наличие manifest, exact entryCount и digest sorted sidecar, включая manifest нулевых записей. Missing manifest/rows, count/digest mismatch, invalid entry/schema/scope или ID collision → safe 500 и rollback. Version 0 исторического snapshot допускает отсутствие manifest/rows; неожиданное наличие journal sidecar у version 0 также отклоняется. Metadata не использует изменяемый afterRevision в digest, поэтому contiguous Undo update не инвалидирует manifest.

Новые task IDs вставляются прежде restore sidecar; restored rows сохраняют оригинальные IDs/text/date/createdAt/updatedAt. Sidecar принадлежит именно снимаемому latest undo sequence и проверяется на соответствие project/task IDs target snapshot и отсутствие collision с активными IDs; corruption → safe 500/rollback, не silent overwrite. Rows восстановлены и journalRevision увеличена один раз до удаления undo snapshot/sidecar/manifest. Session/revision, contiguous previous Undo eligibility и 20-item bound остаются прежними. Failed Undo оставляет sidecar/manifest, tasks, state, snapshots и operations неизменными. Snapshot pruning каскадно убирает и rows, и manifest только соответствующих sequences.

Если Undo создания/другой planning команды удалил бы существующую задачу с более поздними активными journal entries, отклонить целиком с 409 `UNDO_JOURNAL_CONFLICT`: «Отмена удалит задачу с записями журнала. Сначала сохраните нужный текст и удалите записи явно». Никакие rows/snapshots/revision не меняются; верхняя отмена не становится автоматически пустой. После явного journal удаления пользователь может повторить Undo с новым planning operationId и прежней project revision. Это рабочая защита данных, а не новая общая политика планирования. Обычное подтверждённое `task.delete` ветки с записями разрешено и обратимо как выше.

Пример независимости: edit задачи → create записи → Undo edit восстанавливает поля задачи, сохраняет запись. Delete ветки A → edit записи surviving B → Undo delete восстанавливает A и её записи, сохраняя актуальную B. Delete A → exact retry её ранее завершённого create возвращает frozen ack и не воскрешает A. Undo delete → exact retry старого delete возвращает прежний tree ack, не удаляя A повторно; журнал после актуального GET остаётся восстановленным.

Журнальный CRUD не входит в кнопку Undo. Кнопка остаётся в шапке обоих project views; доступное имя и tooltip уточняются до «Отменить изменение плана». Ctrl/Cmd+Z вне inputs продолжает отменять план; внутри textarea — обычная редакторская отмена текста. На вкладке журнала короткая постоянная подпись сообщает: «Записи редактируются и удаляются отдельно; отмена в шапке относится к плану». Не отключать `canUndo` только потому, что создана запись.

Existing historical `beforeSnapshot`, migration archive и cached tree responses не переписывать/расширять. Старый Undo без sidecar восстанавливает задачи обычным алгоритмом и оставляет journal surviving IDs; конфликт удаления заметок применяется и к нему. Planning/legacy replay по exact payload/digest/scope возвращает immutable historical tree, без journal reconciliation, сброса journal revision или пересчёта frozen schedule. В client replay payload никогда не считается authoritative current journal. Защитить эти правила отдельными regression fixtures.

## 7. UI, навигация и черновики

Под названием проекта всегда одинаковые две вкладки «Задачи / Журнал», tablist + ArrowLeft/Right/Home/End; активная вкладка имеет tabpanel. Шапка, строка tabs и область controls имеют одинаковую высоту в обоих видах; журнал заменяет содержимое области, не добавляет меняющуюся строку. В задачах остаются current search/status и list/Gantt controls. В журнале та же шапка содержит отдельный поиск и popover периода. Активные критерии/сброс укладываются в существующую controls строку. Заголовок проекта не повторяется в ленте. Лента имеет дату-группу, plain text cards, task-title button/link и menu edit/delete, кнопку «Добавить запись».

В панели добавить working вкладку «Журнал», сохранить компактную ширину и четыре вкладки на одной строке с доступным переполнением на узком viewport. Task journal показывает только прямые записи выбранной задачи, форму body/date и «Добавить запись», затем groups и «Показать ещё». Date default — existing project-today; при смене today не перезаписывать явно изменённый/dirty draft. Никакой подсказки дат из schedule. Enter в textarea — перенос; Ctrl/Cmd+Enter отправляет валидную форму, keyboard submit и кнопка используют один handler. Inline validation связана aria-describedby; saving/saved/error сообщаются доступным live status.

Project create открывает диалог с выбором любой current task проекта, обязательными date/body. Picker различает одинаковые titles полным parent path и ищет title/path; summary/done доступны. Empty project без задач показывает ясное состояние и disabled add с объяснением. Общий editor используется и для edit (task immutable), и в панели; не дублировать правила даты/валидации/retry. Открытие, Cancel/Escape и успешное закрытие project editor сохраняют underlying journal scroll и геометрию toolbar/cards; modal overlay/scroll lock компенсирует scrollbar, не переводит background scroll в начало. Success refresh сохраняет visible anchor/offset по §5; новый объект не заставляет прокрученную ленту прыгать к началу.

Project/task entry delete открывает подтверждение **одной** записи; после успеха пустая day group исчезает, фокус идёт на следующую menu кнопку, предыдущее соседнее действие либо add при пустой ленте. Editor dialog trap focus, role dialog/aria-modal, Escape, явная отмена и восстановление фокуса на trigger (или add, если trigger исчез). Delete, picker и menu не вызывают selection/drag случайным bubbling.

TaskTree сейчас не имеет общего row menu. Добавить маленькую sibling `⋯` без сдвига title, доступную hover/focus-within и постоянно при отсутствии hover, с пунктами «Открыть задачу», «Добавить запись», «Добавить подзадачу». Быстрое journal действие открывает выбранную task panel на journal и фокус textarea; existing «+ Подзадача»/Shift+Enter и tree keyboard сохраняются, никаких постоянно видимых journal иконок в каждой строке. Действие доступно также в shared subtask tree; draft row меню не имеет.

In-memory state хранит projectView, list/Gantt, collapsed branches, task filters, selected task/tab, Gantt period/scale и scroll positions дерева/Ганта и project journal. Скрытие задач не уничтожает их view state/quick drafts: оставить существующий TaskTimeline mounted hidden или восстановить полный сериализуемый view state через небольшой contract. Возврат «Задачи» восстанавливает оба scroll axes, выбранную surviving task и состояние filters. Task title из project journal открывает panel/journal **поверх той же project ленты**, не меняет view/filter/scroll. Закрытие panel возвращает фокус на origin journal title при его наличии. При отсутствующей задаче после reload selection очищается, черновик не применяется другому ID.

Минимальная браузерная история без router dependency: same-origin `?project=<UUID>&view=tasks|journal&task=<UUID>&panel=details|subtasks|dependencies|journal` и namespaced leaf history state. Explicit project switch открывает «Задачи» с defaults; pushState для project/view и открытия task из ленты; Back/Forward восстанавливают соответствующую session view state и позицию, если объекты ещё существуют. Initial/refresh URL валидируется; неизвестный project даёт safe unavailable state/возврат к списку проектов, чужой task не выбирается. Query/body/drafts/credentials не кладутся в URL или history.state. Auth/login query/history не раскрывают журнал без server session. Доступность scroll restoration после полного refresh не обещается; в рамках текущей client session — проверяется.

Journal create/edit drafts хранятся только в React памяти, с ключом project + task/create либо entry/edit; modal-create имеет отдельный project key. Смена tab/закрытие editor сохраняет draft, повторное открытие возвращает его. Есть явное «Очистить черновик» с подтверждением для непустого текста. Никакой localStorage/sessionStorage/автосохранения несохранённого текста на сервер. Dirty existing plan/detail drafts сохраняются действующими guards: journal tab той же задачи не размонтирует их; выбор другой task/project по-прежнему требует их разрешения. Journal draft не превращается в plan dirty, но входит в beforeunload/logout guard. Logout с journal draft требует явного подтверждения потери; после завершённого logout/401 очищаются private in-memory journal caches/drafts.

Во время journal write disable duplicate submit и competing writes/delete/Undo текущего проекта. При uncertain outcome блокировать editor mutation и переход к другой задаче/проекту до exact retry, показывать причину. После обычной ошибки input остаётся; после 409 active list можно обновить без перезаписи draft. GET uses request sequence/project/filter identity: поздний ответ предыдущего проекта/filter не заменяет текущую ленту или focus. Project/task lists после ack/lifecycle refresh получают одну общую инвалидизацию; current tree не обновляется journal write. При возврате вкладки/фокусе окна refresh journal; cross-tab live push не вводится. Если task удалена другой вкладкой, сохранить draft и сообщить, что запись сохранить нельзя; не переназначать её автоматически.

Перед разрешением entry titles/paths/link targets и project picker сравнить `JournalPage.projectRevision` с revision используемого task metadata. При equality использовать этот набор; при mismatch не рисовать старые названия как актуальные и не считать неизвестный taskId удалённым. Запустить отдельный guarded `GET tree`, не planning mutation. Existing tree GET может вычислить schedule по действующему read контракту; journal repository CRUD/read/replay его не вызывает. Если current planning tree нельзя безопасно обновить из-за dirty/uncertain planning draft, сохранить полученный read-only `{projectId, revision, tasks}` как journal metadata, а planning tree/baseline/sent envelopes не заменять. Из этого revision-matched набора строятся journal titles/path/picker и task journal header; чистое дерево разрешено актуализировать обычным apply. Такой read-only cache не является новым источником writes/CPM.

Publishing coherent page требует **равных** metadata и page projectRevision. Если tree GET новее page, отбросить pending page/cursor и перечитать первую page с прежними filters; если tree старее page, повторить tree GET. Не понижать уже известные revisions. После двух дополнительных согласующих попыток при продолжающейся гонке оставить последнюю coherent ленту помеченной «Данные изменились; обновите журнал», заблокировать её stale task links и picker и предложить явный refresh; не склеивать разные revisions. Initial mismatch/error показывает loading/metadata error без пустых titles, сохраняя полученный pending page и drafts. При успешном согласовании все taskIds должны существовать в matched tasks; отсутствие — безопасная ошибка целостности, не автоматическая удалённая задача. Remote delete между чтениями обновляет page до удаления entries; уже открытый draft удалённой задачи сохраняется и показывает недоступность сохранения.

Guarded refresh сохраняет planning и journal drafts вместе с их исходными baseline revisions, filters, selected task ID/tab, collapse, Gantt state и first-visible anchors/scroll обеих осей. Не вызывает reset-путь обычного project switch. Selection остаётся, если task существует; при удалённой dirty selected task показывается existing removed state, текст сохраняется. Чистая удалённая selection снимается без прыжка ленты. Открытие панели для новой remote task разрешено после coherent metadata refresh и existing planning dirty guards; меню/picker не используют старое дерево. При tree error/repeated race editor text/selection/scroll не теряются и не отправляются никакие плановые команды. Background refresh никогда не изменяет baseline editor/delete confirmation (§4).

Browser popstate с dirty planning draft или unresolved journal operation не уничтожает state: восстановить прежний адрес/навигационную позицию и показать существующее unsaved/retry сообщение. Обычный journal dirty draft может остаться в RAM при Back/Forward, поскольку ключи изолированы. Явный переход/самостоятельный перевод фокуса отменяет поздний async focus restore.

Пустой journal, нет результатов фильтра, loading, failed initial GET, failed load-more, stale cursor, mutation validation/conflict/uncertain и удалённая задача различаются. Load-more error сохраняет уже видимые записи. Add success обновляет обе ленты без дублей; если workDate/body не входят в project filter, показывать «Запись сохранена; она не подходит под фильтр» и не снимать фильтр молча. Длинный body отображать `white-space: pre-wrap` с переносом длинных слов; HTML и ссылки не интерпретировать. Проверять 1440×900, 1280×800, узкую панель, длинные task paths и много entries одного дня.

## 8. Безопасность и ограничения

Журнал — private пользовательские данные наравне с tasks/descriptions. No-store на API, existing CSP/same-origin/session/cookie policy, parameterized SQL, strict output schemas. Не логировать journal body/title/query/workDate, route querystrings, raw requests/responses, cookies, session IDs или replay payload. Only safe error code/request ID. Fixtures/E2E/screenshots только synthetic; не добавлять PNG архива как approved assets. Browser artifacts остаются ignored private outputs, публичные бинарники требуют отдельного точного privacy review по действующему manifest.

Новые journal writes вызывают existing demoLimits admission после strict parse, до repository; все retries в demo учитываются как attempts по D20. Normal mode не получает новых quotas. Demo seed не обязан содержать journal; новая функция работает в общей временной synthetic DB и исчезает после restart как tasks. SQL backups содержат journal, поэтому остаются private. Никаких installs, новых credentials, remote push/deploy или changes scanner policy.
