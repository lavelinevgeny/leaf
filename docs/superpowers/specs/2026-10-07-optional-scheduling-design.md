# Адаптация сроков S2–S3 к C11–C15

Дата: 2026-10-07. Статус: кандидат спецификации для независимого ревью; приложение не адаптировано. Основание — [DECISIONS](../../DECISIONS.md), [SCHEDULING](../../SCHEDULING.md), [UI](../../UI.md), [ARCHITECTURE](../../ARCHITECTURE.md) и [ACCEPTANCE](../../ACCEPTANCE.md).

Положительное ревью этого документа означает согласованность спецификации с зафиксированными требованиями. Оно не является решением владельца по O06, разрешением миграции production или подтверждением готовности V1.

## 1. Цель, границы и происхождение правил

Цель — описать проверяемую замену прежней модели Auto/Fixed необязательными исходными началом, окончанием и длительностью; отделить настоящее расписание от условного отображения и сохранить существующие данные при исключении deadline. Иерархия, FS, Гант и критический путь остаются обязательными для первого релиза.

В объём входят domain/DTO, SQLite и миграция, операции/retry/undo, редактор сроков, сводные даты, полосы и диагностика. Вне объёма: реализация кода в этой задаче, S4 доска/поиск, S5 импорт/экспорт/restore, новые типы зависимостей, лаги, ресурсы, actual/remaining forecast, holidays, новый дизайн подзадач и изменение стека. Новый формат project export в S5 обязан использовать целевую модель, но сам экспорт здесь не создаётся.

| Источник | Нормативное следствие | Разделы / критерии |
|---|---|---|
| C11 | Нет общего назначения сроков от project.startDate; длительность не включает Auto | 3, 6, 7; OS01, OS02 |
| C12 | Только полностью определимый сводный интервал; минимум начал / максимум окончаний | 4; OS05, OS06 |
| C13 / C04 | inputStart, inputFinish и durationDays независимо nullable; название достаточно для создания | 3; OS01–OS03 |
| C14 | Подзадачи без начала получают приглушённую полосу при наличии точки привязки; длительность или один день | 5; OS07–OS09 |
| C15 | В целевых Task, командах, UI и расчёте нет deadline; finish сохраняется | 6–8; OS10–OS13 |
| D13 | Минимум известных начал в той же родительской группе; display не сохраняется и не участвует в summary/CPM | 4, 5; OS05, OS07–OS09 |
| D04–D06, D08, D11–D12 | Календарные дни, leaf-only FS, summary не работа, статус не длительность, серверная отмена/прогноз | 3, 4, 6, 8 |
| C05 / O06 | CPM остаётся обязательным; его новая математическая политика ещё не утверждена | 9; OS14–OS16, gate G-CPM |

C11–C15 подтверждены владельцем. D13 и другие D — рабочие defaults. Правила W01–W06 ниже — технические предложения этой спецификации, допускающие отдельный пересмотр; они не добавляют записи C и не закрывают O06. Принятие агентами документа не превращает W в решения владельца.

Согласованный объём можно подготовить и проверить отдельно от G-CPM. Полную адаптацию, production-переключение и релиз нельзя объявлять завершёнными, пока gate не закрыт и новый CPM не проходит приёмку.

Зоны связности при будущей реализации: новая SQL migration должна входить в registry, `.dockerignore` и `scripts/package-check.mjs`; `requiresWorkPreservation` должен учитывать duration-only без legacy mode/deadline. `intervalOf` сейчас одновременно используется Гантом и реальными labels/графом: conditional interval нельзя отправлять в обычную подпись сроков или доступный диапазон реального расписания. Это ограничения контрактов, не расширение scope.

Изменение только поля в форме или удаление колонки deadline недостаточно: strict response schema отклонит старый cached response, а undo способен вернуть старую модель. В migration 002 были удалены operations/undo_snapshots; повторение такого удаления не соответствует сохранности этой адаптации.

## 3. Исходные сроки и реальный интервал

### 3.1. Целевые исходные данные

Конечная задача содержит `inputStart: CalendarDate | null`, `inputFinish: CalendarDate | null`, `durationDays: positive integer | null`. Пропуск поля в patch сохраняет прежнее значение; явный `null` очищает только его. Создание задачи задаёт все три значения `null`. Ни пустая строка, ни неизвестность не означают 0 или 1. Сводная задача не хранит собственную работу; признаки summary выводятся из детей.

`CalendarDate` — валидная строка `YYYY-MM-DD` в существующем диапазоне 0001–9999. Окончание включительно. Календарь проекта сохраняется: `all-days` или `weekdays` (пн–пт), default D04; timezone нужен для «Сегодня», не для арифметики дат. Существующие чистые календарные функции сохраняются; арифметика через UTC-midnight/24 часа запрещена.

W01 — консервативная трактовка неполного ввода до закрытия G-CPM: реальным интервалом считать только пару заданных, допустимых дат. `start + duration` и `finish + duration` сами по себе не заполняют недостающую дату, не дают полного интервала для summary/CPM и не запускают Auto. Обоснование: C13 разрешает пустые поля, а C11 отменяет автоматическое назначение; новый вывод границ отдельно не согласован. Возможный вывод для анализа без записи исходных данных обсуждается в G-CPM; его выбор потребует обновить W01 и примеры.

| start | finish | duration | Согласованное хранение / W01 анализ | Гант |
|---|---|---|---|---|
| null | null | null | Без расписания | Без полосы, кроме C14 |
| задано | null | null | Только исходное начало | Отметка начала |
| null | задано | null | Только исходное окончание | Отметка окончания; при C14 также условная полоса |
| null | null | задано | Только длительность; Auto не включается | Только условная полоса при C14 |
| задано | null | задано | Окончание неизвестно | Отметка начала; полный реальный интервал не рисуется |
| null | задано | задано | Начало неизвестно | Отметка окончания; условная полоса при C14 |
| задано | задано | null | Реальный интервал, производная calendarSpanDays | Обычная полоса по датам |
| задано | задано | задано | Реальный интервал при согласованной тройке по W02 | Обычная полоса по датам |

`calendarSpanDays` — производное число рабочих дней включительно; его вычисление не записывает пользовательское `durationDays`. При обеих датах и пустой длительности UI может показывать отдельную подпись «По датам: N дней», оставляя поле длительности пустым.

### 3.2. Валидация и противоречия

W02 — не выбирать скрыто один из трёх источников. Для нового ввода полного интервала проверять `finish >= start` и рабочие границы в `weekdays`, как у прежнего Fixed. При обеих датах и заданной duration требовать `durationDays == workingDaysInclusive(start, finish, calendarType)`. Несогласованная тройка возвращает `DURATION_MISMATCH`; неверная пара — `INVALID_INTERVAL`. Вся команда, включая текст/статус, откатывается; UI сохраняет черновик. Пользователь может явно очистить duration или изменить одно из значений. Длительность 0/отрицательная/дробная отклоняется; существующий предел вводимой duration 1 000 000 остаётся техническим default, а производная длительность пары ограничена диапазоном дат.

Одиночная дата остаётся календарной пометкой и может приходиться на выходной; она не создаёт рабочий интервал. Если позже введена вторая граница, применяется проверка полного интервала. Не нормализовать пользовательские границы молча.

При смене календаря сохранять исходные даты/длительность, не назначать другие даты. Несовместимая уже сохранённая пара/тройка получает диагностику и не используется как валидный рабочий интервал до явного исправления. Миграция также сохраняет невалидный legacy ввод с диагностикой, а не исправляет и не удаляет его. FS-конфликт при валидных датах отличается от неверного интервала: даты остаются реальными и видимыми, даже когда план infeasible.

Done не обнуляет длительность и не разрешает скрытого переноса. Сохраняется существующий защитный сценарий: изменение исходных сроков done требует явного возврата в todo/doing; составная task.edit может вернуть статус и изменить поля атомарно. Неполную задачу допустимо отметить done без выдуманного интервала. Completed dates/indices S2 — legacy locks, не новые actual dates.

## 4. Сводные сроки и неполнота

W03 — полный интервал родителя определяется по всем его конечным потомкам, включая скрытые/свёрнутые, а не только видимым строкам или найденным фильтром. Каждый конечный потомок должен иметь валидный реальный интервал по выбранной политике; условное размещение никогда не выполняет это условие. Обоснование: D06 исключает собственную длительность summary, C12 запрещает частичный диапазон.

Если условие выполнено: `summary.start = min(real starts)`; `summary.finish = max(real inclusive finishes)`. Длительность summary — календарный охват, не сумма параллельных детей. Данные дочерних summary эквивалентны агрегации по конечным потомкам; произвольная глубина не меняет результат.

Если хотя бы один конечный интервал отсутствует/невалиден: обе публичные summary границы `null`; нет диапазона в дереве, панели, графе и полосы summary. Можно показать причину «Сроки этапа не определены: N из M задач с полным интервалом», без частичного диапазона. Внутренний известный минимум для display C14 не является summary date.

FS-конфликт не стирает валидный исходный интервал: summary может показывать полный диапазон вместе с infeasible-диагностикой. Coverage отдельно считает конечные работы с валидным реальным интервалом; summary не входят в знаменатель. Unknown в связанной цепи делает оценку FS/CPM неполной, но не стирает заданные даты соседей. Известные независимые даты всегда видимы. Само наличие незапланированной несвязанной задачи не превращает её длительность в ноль и не создаёт общий прогноз завершения всех задач.

При добавлении первого ребёнка к работе с любой датой/длительностью, done или связями требуется существующий `preserveWork`: сохранить собственную работу отдельным work-child, перенести обе стороны связей и исходные поля одной транзакцией. Legacy archive не становится собственным планом родителя. При удалении последнего ребёнка родитель становится конечной задачей с тремя `null`; вычисленный summary интервал не материализуется. Undo возвращает весь прежний исходный план.

## 5. Условное отображение Ганта

Три утверждённых PNG действительно просмотрены. Сохраняются светлый экран, единые видимые строки дерева/Ганта и компактная правая панель; поля/неточные даты рисунков не расширяют scope. Исключённый коллаж не использован.

Для каждой **родительской группы** вычислить отдельный `knownStartMin`: минимум заданных inputStart всех конечных потомков этой группы. Для конечного непосредственного ребёнка берётся его inputStart, для сводного ребёнка — известный минимум его ветви; затем `anchor = min(knownStartMin непосредственных детей)`. Это включает известное одиночное начало. Внутренний минимум может существовать при полностью скрытом summary интервале; он остаётся display-опорой и не публикуется как summary.start. Display начала в knownStartMin не входят. Группа определяется данными, а не видимыми строками; дата соседней внешней ветви не даёт anchor группе без собственных известных начал. Это W04 — техническое уточнение D13 для вложенных групп. У корневой задачи `parentId = null` нет родителя: общий минимум проекта не создаёт ей условную полосу.

Конечная подзадача с `inputStart = null` и известным anchor получает отдельную display-проекцию:

- `displayStart = anchor`;
- при заданной duration длина — duration рабочих display-дней; при отсутствии duration ровно один календарный display-день;
- `displayKind = conditional`, доступная подпись «Условное размещение; начало не задано»;
- исходные start/finish/duration остаются прежними, реальные schedule fields не заполняются.

W04 также фиксирует геометрию: первый display-день занимает сам anchor, следующие дни идут по календарю проекта. Поэтому при anchor в пятницу и duration=2 в `weekdays` displayFinish — понедельник; при одиночном субботнем anchor и duration=1 полоса занимает субботу, duration=2 заканчивается в понедельник. Это только проекция рисунка, не допустимый рабочий интервал. Переполнение 9999-12-31 не порождает неправильную дату: полоса ограничивается поддерживаемым окном, сопровождается подписью об ограниченном отображении; source duration не меняется.

Известное inputFinish не ограничивает условную полосу и не становится её вторым источником длины: правило C14 использует duration или один день. Исходное окончание остаётся отдельно читаемой пометкой/полем, даже если не совпало с displayFinish. Обе заданные даты имеют приоритет и рисуют обычную полосу. Без anchor строки без начала не получают полос; одинокая дата показывается пометкой, а не вехой нулевой длительности.

Условные полосы не участвуют в summary, FS, coverage или CPM, не создают критические ID, не используются концами зависимостей как реальные даты. Сам граф FS остаётся видимым и у задач без дат. При отсутствии реального конца стрелку на временной шкале не выводить из условного края; связь доступна в выбранной схеме с подписью неполноты. Условную полосу нельзя drag/resize в качестве плана; ввод выполняется через поля. Изменение anchor или duration может переместить display без операции сохранения и без появления отдельного undo.

## 6. Целевой API и атомарные изменения

Точная форма версионирования и SQL миграции — техническое предложение W05, которое исполнитель оформляет отдельным небольшим ADR до изменения схемы. Целевой публичный DTO не содержит `deadline`, `notBefore`, `planMode`, `project.startDate` и relative completed indices. В целевой модели Project остаются id/title/revision/calendarType/timezone и служебные timestamps; Task содержит структуру/текст/статус и три необязательных исходных поля. Архив совместимости — отдельный внутренний тип, не часть Task DTO.

`task.edit` сохраняет текст/статус и patch трёх полей одной командой; старые task.plan с mode и project.schedule.startDate не принимаются целевым контрактом. Настройки календаря/timezone остаются, название команды может сохраниться без startDate. Неизвестный/legacy field не игнорируется: ответ `CONTRACT_VERSION_CONFLICT` или явная ошибка схемы, без частичного применения. Повтор уже применённой старой операции обрабатывается отдельно по разделу 7.

Ответ tree/schedule содержит ревизию, реальные интервалы, summary nullable, coverage, diagnostics и явное `analysisStatus`. Display-проекция имеет отдельный тип и не смешивается с реальным schedule. Согласованный источник anchor и проекции — server pure module; React рисует готовые значения и вычисляет только координаты/видимое окно. Имена полей нового ScheduleResult и версия DTO фиксируются в ADR; семантика unknown/conditional/pending-policy обязательна независимо от имён.

До G-CPM `analysisStatus = pending-policy`, floats отсутствуют, criticalTaskIds/criticalDependencyIds пусты; UI объясняет отсутствие расчёта. Это промежуточное состояние разработки, не реализованный C05 и не releasable V1. Нельзя возвращать старый CPM с новой подписью или выдавать empty arrays за доказанное отсутствие критических работ.

Авторитетные записи, проверка графа, пересчёт, result и undo — одна SQLite-транзакция с `expectedRevision`/`operationId`. Invalid input/cycle/schema conflict откатывает также текст, статус и history. Валидные явные даты с FS-противоречием могут сохраняться с infeasible-диагностикой, как в S2; сервер не двигает их. 409 после другой вкладки не теряет новые изменения. Старый сетевой ответ не перезаписывает более новую ревизию; версия контракта проверяется до применения снимка.

W05 для обычных полос: жест доступен только для валидной пары todo/doing. Перенос сдвигает обе исходные даты на одинаковое число рабочих дней; resize меняет соответствующую исходную границу. Заданная duration не изменяется скрыто: resize с несовпадением предлагает явное синхронное изменение/очистку duration до отправки составной команды. Summary/done/conditional и неполные интервалы не имеют этих жестов. Один жест — один intent и одна отмена; клавиатура/поля дают ту же операцию. Жест не создаёт notBefore и не сдвигает FS соседей. Эта механика — техническое предложение, а не новый owner decision.

## 7. Совместимость persisted данных, history и undo

### 7.1. Сохранность и адаптация

W06 — минимально безопасное предложение: новый версионированный слой совместимости сохраняет исходные legacy данные **внутри той же private SQLite БД** в отдельном migration archive. Это не внешний export, не JSON в репозитории и не новый пользовательский deadline. Архив недоступен активным Task/API/CPM/UI и не попадает в будущий project export. Содержимое архива нельзя логировать.

Миграция в одной транзакции архивирует исходные проектные scheduling поля, task planning поля и исходные JSON-тексты operations.payload/response и undo_snapshots.beforeSnapshot с ключами/версиями, затем создаёт целевую проекцию. Не использовать ON DELETE CASCADE от active Task для архивных записей: последующий delete/undo не должен уничтожить данные миграции. Прежний snapshot может содержать удалённую задачу; адаптация обрабатывает все снимки, а не только текущие task rows. Проверять row counts, связи и digest исходных сериализаций без вывода содержимого. Архивирование auth/session/password данных не требуется; их строки и отношения остаются нетронутыми.

Из legacy активной проекции сохраняются ids, parent/order, title/description/status, inputStart/inputFinish и durationDays, calendar/timezone, dependencies. Deadline **не** превращается в inputFinish, notBefore **не** превращается в inputStart, project.startDate **не** назначает даты задач. Legacy Fixed с пустой пользовательской duration сохраняет прежнее сохранённое значение duration, но новые задачи с двумя датами не обязаны его материализовать.

Legacy Auto с null input dates остаётся задачей с известной duration и неполным реальным интервалом; прежние вычисленные даты не объявляются пользовательским вводом. Старый результат сохраняется только в архиве. Это сохраняет исходные данные, но меняет доступность прежнего Auto-расписания; до production применения нужна явная проверка количества таких задач и совместимости миграции на synthetic cases. Если владелец выберет перенос старого вычисленного Auto-интервала в явные поля, это отдельная политика G-MIGRATION: preview и подтверждённая атомарная конвертация, без восстановления Auto и без назначения дат новым задачам.

Persisted completedStart/Finish done-задач — отдельный случай G-MIGRATION: они сохраняются в архиве; нельзя молча подменить ими input dates или выкинуть завершённый план из обещания совместимости. Completed relative indices без абсолютного начала проекта невозможно превратить в CalendarDate без придуманной опоры. До выбора политики активного представления done locks миграция production заблокирована, а синтетические проверки сохранности допустимы.

Нужны отдельные gates: G-CPM решает математический смысл нового анализа; G-MIGRATION решает активное представление имеющихся Auto/done интервалов. Они могут закрываться разными решениями; положительное document review ни одного не закрывает. Рекомендуемый безопасный preview показывает только агрегированные числа категорий и synthetic примеры, не реальные task titles в public отчёте.

### 7.2. История операций и точный retry

Существующее правило идемпотентности сохраняется: ключ operationId уникален; project/session и канонический payload должны совпасть, иначе `OPERATION_REUSED`. Для migrated legacy операции сравнение выполняется с сохранённой canonical legacy payload, даже если этот payload больше не принимается для новой команды. Уже применённая операция не применяется снова, не создаёт новую revision и не добавляет undo.

Cached legacy response нельзя вернуть целевой strict schema или клиенту как есть. Adapter выдаёт целевой DTO соответствующего исходного response snapshot/revision, с анализом новой версии либо pending-policy. Он не заменяет результат последним snapshot проекта: повтор должен сохранять смысл исходной операции, а revision guard клиента защищает от stale response. В response нет deadline/mode/notBefore/project start; originals доступны только compatibility adapter. Идентичный operationId с изменённым или новым versioned payload отклоняется; версия входит в новую canonical форму.

Пример replay: legacy операция X применена при revision 8 и вернула revision 9 с deadline. После миграции другая операция Y довела проект до 10. Точный retry X возвращает адаптированный snapshot revision 9 без deadline, не 11 и не 10; БД остаётся на 10, X не добавляет запись undo, UI не заменяет видимую revision 10 старой. Иной payload с X получает 409. Это сохраняет outcome, а не старые байты публичного response.

Существующий S3-клиент unversioned: в `src/client/api.ts` нет handshake и version header, а его strict успешный DTO несовместим с target. Новый сервер не может исправить уже загруженный бинарник. W05 задаёт server boundary: запросы к project API (включая list/create/rename/tree/schedule/commands) обязаны иметь transport header `X-Leaf-Contract-Version: 2`. При отсутствии/неподдерживаемой версии сервер возвращает **HTTP 426** и прежний strict error DTO `{code: "CONTRACT_VERSION_CONFLICT", message: "Версия приложения устарела. Обновите страницу для продолжения. Этот запрос не изменил данные."}`. Проверка выполняется после существующих auth/origin checks, но **до** project mutation, записи operation/undo, выдачи target DTO и чтения legacy cached response. Auth/session endpoints сохраняют прежний совместимый контракт; отказ версии не ослабляет их защиту.

Статус 426 выбран с учётом реального S3: non-2xx parser принимает `{code,message}` без списка известных codes и создаёт ApiError с uncertain=false; App показывает message для такого статуса. HTTP 409 здесь не подходит: App подменяет его текст общей ошибкой ревизии. Таким образом действительно старый клиент увидит просьбу обновить страницу, а не успешный несовместимый DTO/INVALID_RESPONSE или ложную неопределённую новую мутацию. Это не обещает ему автоматический handshake, сохранение черновика после browser reload или новый replay-интерфейс. Не отправлять ему legacy response как bridge, содержащий исключённые активные поля.

После обновления target-aware клиент передаёт version header для обычных запросов. Для точного повтора сохранившегося legacy envelope он дополнительно передаёт transport header `X-Leaf-Legacy-Replay: 1` и **неизменённый** оригинальный body. Replay branch допускает только поиск уже применённой archived операции с совпадающими operationId/project/session/canonical payload; неизвестная операция отклоняется без выполнения старой команды. Здесь transport version/replay headers не добавляются в canonical archival legacy payload и не меняют исходное сравнение. Для новых target операций версия входит в новую canonical форму, как указано выше; это отдельный формат. Target-aware клиент получает только адаптированный target DTO исходной revision. Потерянная старая команда до upgrade не повторяется как новая операция автоматически; отсутствие доступного исходного envelope не компенсируется придуманным payload. Сервер обязан отличать «ещё не применено и больше не допустимо» от «уже применено — exact replay»; после отказа/обновления пользователь может проверить актуальный проект перед новым явным действием.

### 7.3. Undo, revision и rollback

Undo snapshot адаптируется тем же детерминированным mapper, что active snapshot. Отмена восстанавливает целевые исходные поля, дерево/связи/настройки; не возвращает deadline в Task/API/UI и не включает Auto. Original snapshot сохраняется в архиве для доказуемого восстановления исходной формы и контроля миграции. После undo результат пересчитывается текущим алгоритмом, а номер revision увеличивается как прежде; stale undo после другой сессии получает 409.

Нельзя очищать operations/undo_snapshots и называть это полной preservation. D11 допускает отсутствие undo после перезапуска, но не разрешает потерю исходных сроков или случайную повторную мутацию из-за удаления idempotency records. W06 сохраняет имеющиеся записи и адаптирует их; будущий срок хранения отдельно следует существующим границам history.

Миграция повторно не выполняется при записанной schema version; ошибка на любой стадии откатывает archive и active изменения вместе. Application-start и миграция fail closed при неизвестной legacy версии/повреждённом JSON, не открывают частично адаптированную БД. Downgrade старым бинарником не поддерживается поверх новой schema: явный отказ, без попытки читать новый DTO. Production rollback использует consistent private backup предыдущего экземпляра по DEPLOYMENT/PRIVACY; archive не объявляется готовой функцией restore S5. Проба всех сценариев — только на disposable synthetic SQLite; production data агент не читает.

## 8. FS, конфликты, UI и пересчёт

Граф остаётся DAG с leaf-only FS, lag=0, внутри одного проекта; parentId не создаёт precedence. Self-link, duplicate, summary endpoints, foreign project и cycle отклоняются до commit с объяснимой цепочкой. Перемещение ветки не создаёт/удаляет FS, кроме явного preserveWork переноса endpoints.

Для FS достаточно известных календарно допустимых predecessor.inputFinish и successor.inputStart; наличие остальных краёв и duration не требуется. Недостающие остальные поля могут оставить CPM неполным, но не мешают проверить это конкретное условие. Рабочие границы переводить в индексы с технической внутренней origin, выбираемой из реальных дат, а не из project.startDate. Origin не является input, не ограничивает ранние задачи и не видна как «начало проекта». FS условие: `successor.startIndex >= predecessor.finishExclusiveIndex`; окончание включительно. В пн–пт после пятницы допустим понедельник; в all-days — суббота.

Нарушение FS даёт `EXPLICIT_PRECEDENCE_CONFLICT` с task/edge IDs и видимой диагностикой; поля сохраняются и не сдвигаются. Неизвестная необходимая граница или граница на нерабочем дне выбранного календаря не даёт проверяемого рабочего FS: `UNKNOWN_PRECEDENCE` или календарная диагностика соответственно, не успех и не нулевая работа. Реальная дата известного successor не пропадает при неизвестном predecessor. Coverage, неполнота связи и невозможность CPM — разные признаки. Когда есть доказанный конфликт и unknown одновременно, feasibility = infeasible с обеими диагностическими причинами; иначе unknown связанный контекст = incomplete. Пустой проект имеет нулевой coverage и никакого выдуманного окончания.

У UI три необязательных поля, отдельного дедлайна нет ни в деталях, ни в графе/tooltip/доступных подписях; нет DEADLINE_EXCEEDED. Auto/Fixed/«не раньше» и общий блок «План проекта» с startDate удаляются из целевого пользовательского сценария. Календарь и timezone остаются доступными в настройках. Summary поля нередактируемы; partial не даёт диапазона. Статус и критичность остаются независимыми.

Пересчёт после source dates/duration/status, структуры, зависимости и календаря; display пересчитывается также при изменении sibling anchor. Переименование, sibling order, collapse/filter и масштаб Ганта не меняют реальное расписание. Проверить loading/empty/error/offline, dirty panel, точный retry, удаление выбранной задачи, focus restore, Tab/Esc, доступную подпись условных полос и клавиатурную альтернативу жестам. Перед server response не показывать «Сохранено».

## 9. G-CPM: граница неразрешённого O06

C05 требует настоящий пересчитываемый критический путь в V1. C12 summary range не заменяет CPM; максимальное окончание явно датированных задач не доказывает критичность. Старыми Auto fixtures нельзя легитимировать новый алгоритм без выбора политики.

Владелец должен выбрать математическую семантику, затем зафиксировать её в DECISIONS и небольшом ADR с независимыми expected cases. Gate содержит следующие проверяемые решения:

1. По каким входам работа допускается в CPM: только валидная пара или также duration с одним/без краёв; допускается ли вывод отсутствующей границы только для анализа, без записи источников? Решение меняет W01.
2. Что означают явные даты: фактические заданные положения, ограничения release/lock или только календарная привязка длительности? Никакой вариант не возвращает общее автозаполнение source dates по project.startDate.
3. Что является общим горизонтом обратного прохода и учитываются ли gap/waiting days? Все независимые компоненты должны сравниваться по одной выбранной политике, а не автоматически получать каждый собственный нулевой float.
4. Значение projectFloat и отдельного constraintFloat при жёстких датах/done; чем UI объясняет их различие? Нулевая изменяемость заданной даты не делает каждую работу критической.
5. Какие результаты допустимы для unknown и infeasible: охват, частичные множества и обязательные подписи. Фальшивый полный критический путь запрещён; diagnostic IDs не подменяют critical IDs.

Рассмотрены три подхода; это варианты, а не утверждённый алгоритм:

| Вариант | Польза | Цена / риск |
|---|---|---|
| Анализ явно размещённых интервалов, без сдвигов | Сохраняет смысл введённых дат; можно отделить резерв до общего конца от запрета переноса | Требует определить gap, horizon и смысл float для всех зафиксированных дат |
| Отдельный относительный CPM по длительностям, даты как справка | Даёт классический longest-path анализ без назначения source dates | Может расходиться с показанным Гантом; нужно явное пояснение и политика unknown |
| Аналитические earliest dates с release/locks, без записи источников | Ближе к прежнему проверенному модулю | Легко вернуть отменённый Auto под новым именем; UI должен ясно различать введённые и аналитические даты |

Рекомендация для обсуждения — анализ явно размещённых интервалов; минимально отдаляет граф от того, что видит пользователь, и не назначает сроки. Выбор варианта и его математики **не сделан** этим документом. Нельзя реализовать рекомендацию как окончательное разрешение O06.

После gate алгоритм остаётся чистым, детерминированным и серверным. Обязательны multiple/equal critical paths как множества task/edge IDs без экспоненциального перечисления; tight edge определяется согласованной математикой, не только цветом двух соседей. Сводная критичность — индикатор наличия критических конечных потомков; summary не вершина CPM. Смена дат глубокой работы должна пересчитывать соответствующий граф и UI одной ревизией.

## 10. Независимые синтетические примеры

Это арифметические expected cases для будущих application tests, а не результат нынешнего scheduler. Все даты/задачи синтетические. W01–W04 помечены явно; после gate меняющиеся cases пересматриваются с описанием причины. Существующие `fixtures/scheduling/cpm-cases.json` — исторические Auto-примеры; `calendar-cases.json` остаются проверкой календарной арифметики. Kit checker не проверяет нижеследующие примеры и не считается их application test.

### N01: optional input и согласованная тройка

Календарь weekdays. A: start=2026-10-09 (пятница), finish=2026-10-12 (понедельник), duration=null. Реальный span=2; duration остаётся null. Задать duration=2 — валидно; duration=3 — DURATION_MISMATCH и откат всей команды. Очистить finish — start и duration=2 сохраняются, полного интервала по W01 больше нет. Ни 2026-10-12, ни другое окончание автоматически не записывается.

### N02: summary и приглушённая полоса

P имеет три конечных ребёнка, weekdays: A=[2026-10-05, 2026-10-06], duration=null; B=[2026-10-09, 2026-10-12], duration=null; C=(start=null, finish=null, duration=3). Anchor группы = 2026-10-05. C рисуется условно 5–7 октября; реальные даты C остаются null; coverage=2/3; обе границы P=null. Очистить duration C — display только 5 октября; coverage и summary прежние. Ввести C=[2026-10-07, 2026-10-09], duration=3 — все реальны, P=[2026-10-05, 2026-10-12], span=6 рабочих дней (не 2+2+3=7). Удалить finish B — диапазон P исчезает; display C остаётся настоящей полосой.

### N03: вложенность, отсутствие anchor и одиночное окончание

P содержит summary Q и конечную B без начала. В Q только A=(start=2026-10-05, finish=null, duration=null). По W03 Q и P не имеют сводного диапазона; отдельный knownStartMin Q=5 октября по W04 даёт anchor группе P, поэтому B получает условную полосу на 5 октября. В Q безначальная C получает ту же опору A=5 октября; отсутствие summary интервала её не удаляет. После удаления единственного inputStart A обе группы теряют anchor и условные полосы исчезают. После этого, если B имеет только finish=2026-10-02 и в группе P появляется dated D=[2026-10-09, 2026-10-09], B получает условную полосу на 9 октября и сохраняет отдельную пометку окончания 2 октября. Это не сдвиг finish и не FS-конфликт. Два root leaf без родителя не используют общий проектный anchor.

### N04: календарь display и FS

Weekdays, anchor=2026-10-09, conditional duration=2: display 9–12 октября; без duration — только 9 октября. Реальный A=[2026-10-09, 2026-10-09] и B=[2026-10-12, 2026-10-12], A→B: валидная FS. B=[2026-10-09, 2026-10-09]: EXPLICIT_PRECEDENCE_CONFLICT, обе задачи и исходные даты сохранены. В all-days B=2026-10-10 допустима. Неизвестный start B не проверяется по muted anchor и даёт UNKNOWN_PRECEDENCE. Только finish A=9 октября и только start B=12 октября достаточны для проверки самой FS, но обе задачи всё ещё без полных интервалов для summary/CPM по W01.

### N05: хранение deadline и history

Legacy A: inputFinish=2026-10-06, deadline=2026-10-20. После целевой проекции inputFinish по-прежнему 6 октября, deadline отсутствует в DTO. Legacy B: inputFinish=null, deadline=2026-10-20 — finish остаётся null. Exact archived значения восстанавливаются в synthetic контрольном чтении archive; ни одной копии deadline нет в public response. Старый undo snapshot, содержащий только B с deadline, также адаптируется с finish=null. Legacy replay X revision 9 после текущей revision 10 ведёт себя точно как в 7.2; повтор не создаёт новую мутацию.

### N06: пример, различающий варианты O06

Рабочие индексы от технической 2026-10-05: A=[0,2), B=[5,6), C=[0,10), A→B; длительности 2,1,10. Датированный план имеет gap 3 дня и максимальный finishExclusive=10. Гипотетический обратный проход от 10 по наблюдаемым ES без закрепления LS даёт B LS=9/float=4, A LS=7/float=7, C LS=0/float=0. Ограничение B.start=5 оставляет A только 3 дня до B; само B перемещать нельзя. Относительный longest-path по durations без календарных gaps имеет длины A→B=3 и C=10. Эти арифметические различия показывают, что резерв до общего конца, допустимая задержка до даты B и длина цепи — разные величины; **ни один из этих результатов не объявлен целевым CPM до G-CPM**. Вариант, который делает A/B/C критическими только из-за закрепления каждой даты, неприемлем по сохранённому инварианту SCHEDULING.

## 12. Результат документальной задачи и передача плану

Эта задача меняет спецификации, ссылки и статус; schema, code, lockfile, fixtures и runtime не меняются. Исторические планы S2–S3 не переписаны как выполненная адаптация. План реализации создаётся отдельным агентом после положительного независимого ревью кандидата; он должен отдельно выделить согласованный объём, выбор G-CPM/G-MIGRATION и проверки до production-переключения. Незакрытый gate — конкретная зависимость плана, а не незаметный технический default.

Документальное ревью проверяет traceability, отсутствие противоречий, сохранность всех persisted форм, численные примеры и исполнимость критериев. Вердикт и проверенная ревизия фиксируются фактически после получения результата; до того одобрение не заявляется.

Ревью раунда 1 на `f31e29a`: требования — APPROVED; техническая совместимость — CHANGES_REQUIRED. Закрыты два blockers: server-side отказ для действительно unversioned S3 через HTTP426 до mutation/target DTO/cached response и transport-only target-aware exact replay без изменения archival canonical payload; дополнительно согласованы nullable duration в A12 и явные FS-даты в A07. Раунд 2 на `69b05dca5cf0c2c248eb9843b38f4f5b6f91c857`: требования — APPROVED; техническая совместимость — APPROVED. Это документальное одобрение не закрывает G-CPM/O06 или G-MIGRATION и не начинает реализацию.
